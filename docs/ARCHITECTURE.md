# MetaJetCore — метаоркестратор Claude Code внутри JetBrains IDE

**Статус:** техническое задание, версия 2
**Дата:** 2026-08-29
**Платформа:** Claude Code 2.1.251+, JetBrains IDE **2026.2+** (переработанный терминал),
подписка Claude Team/Enterprise

---

## 1. Что это

Оркестратор — отдельная сессия Claude Code, с которой разговаривает разработчик. Она сама
создаёт рядом с собой вкладки с другими **полноценными** сессиями Claude Code (имплементер,
ресерчер, ревьювер), раздаёт им задачи, отвечает на их вопросы и сводит результат.
Разработчик читает и пишет только в одну вкладку — оркестратора.

Не субагенты и не agent teams. Именно независимые долгоживущие сессии.

### 1.1 Почему не субагенты

Субагент стартует с холодного контекста и каждый раз заново ресерчит то, что уже было
выяснено; при повторном запуске по той же теме он повторяет исследование целиком.

Долгоживущий имплементер накапливает контекст задачи. Когда ревьювер нашёл проблему,
оркестратор кидает правку **в того же имплементера**, и тот уже знает всё окружение —
правка стоит один короткий ход вместо полного повторного ресерча. Это и есть главный
экономический аргумент за схему.

### 1.2 Почему не agent teams

Штатная экспериментальная фича `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` близка по смыслу, но:

- режимы отображения только `in-process` (всё в одном окне) и `split panes` — **только
  tmux/iTerm2**; в терминале IDE и в Windows Terminal не работает;
- `teammateMode` не расширяемый — свой режим отображения не подключить;
- экспериментальная: нет resume in-process teammate-ов, лид фиксирован, нет вложенных команд.

Берём слой ниже — **cross-session messaging**. Он стабильный и работает с независимыми
сессиями в любом терминале.

## 2. Проверенные факты о платформе

Всё в этом разделе проверено на машине (Claude Code 2.1.250, native Windows), а не взято
из документации. Помечено, что именно подтверждено экспериментом.

### 2.1 Реестр сессий

Каждая сессия пишет `~/.claude/sessions/<pid>.json`:

```json
{"pid":16404,"sessionId":"eaee88b1-3dd1-4c6a-8e10-347a3072db59","cwd":"…",
 "version":"2.1.250","kind":"interactive","entrypoint":"sdk-cli",
 "name":"mjc-envtest3","agent":"Explore","status":"idle",
 "messagingSocketPath":"\\\\.\\pipe\\LOCAL\\cc-msg-3a4262713a32975a8a2a19e718f326bc",
 "peerProtocol":1,"peerFeatures":["notify_idle","artifact_yield"]}
```

Это **источник правды** для плагина: связка `pid ↔ sessionId ↔ name ↔ cwd ↔ status`.
Файл появляется при старте и удаляется при выходе, поэтому по нему определяются и момент
готовности сессии, и факт её смерти.

Транспорт сообщений: на native Windows — именованный пайп `\\.\pipe\LOCAL\cc-msg-<hash>`,
на macOS/Linux — unix-сокет. Через серверы Anthropic такие сообщения не ходят.

> **Важно для Linux-сборки.** Сессия внутри WSL 2 и нативная Windows-сессия друг друга не
> видят: разные домашние директории и разные типы сокетов. Все агенты должны жить в одном
> мире. То же касается контейнеров.

### 2.2 Конфигурация через переменные окружения — ПРОВЕРЕНО ЭКСПЕРИМЕНТОМ

Ключевой результат для этого проекта.

Кастомная обёртка вокруг `claude` (лежит в `/usr/local/bin`, сначала поднимает мост, потом
вызывает claude-code) не пробрасывает `"$@"` — все флаги теряются. Но **окружение наследуется
процессом прозрачно**, независимо от того, что делает обёртка.

Тестовый запуск:

```bash
CLAUDE_CODE_SESSION_NAME=mjc-envtest3 \
CLAUDE_CODE_SESSION_ID=11111111-2222-4333-8444-555555555555 \
CLAUDE_CODE_AGENT=Explore \
claude -p --output-format json "reply with exactly: ok"
```

| Переменная | Результат | Вывод |
|---|---|---|
| `CLAUDE_CODE_SESSION_NAME` | в реестре `"name":"mjc-envtest3"` | ✅ работает |
| `ANTHROPIC_MODEL` | заменяет `--model` | ✅ |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | присутствует в бинарнике | ✅ |
| `CLAUDE_CODE_AGENT` | в реестре `"agent":"reviewer"`, но роль **не применена** | ⚠️ только запись в реестр |
| `CLAUDE_CODE_SESSION_ID` | фактический id `eaee88b1-…`, не заданный | ❌ не работает |

**Имя сессии — это адрес для `SendMessage`.** Значит `CLAUDE_CODE_SESSION_NAME` в одиночку
решает задачу адресации: плагин назначает агенту адрес, не трогая argv и не завися от обёртки.

`sessionId` через env задать нельзя — плагин **читает его из реестра** после старта, находя
запись по имени, которое сам же и назначил.

### 2.2.1 Роль через env задать нельзя — проверено

`CLAUDE_CODE_AGENT` записывает значение в поле `agent` реестра, но **определение роли не
подхватывает**. Контрольный опыт в этом проекте:

```bash
# env — роль НЕ применена, ответ generic
CLAUDE_CODE_AGENT=reviewer claude -p "what is your role and lens?"
> I'm a software engineering agent here to help you write, fix, and improve code…

# флаг — роль применена
claude --agent reviewer -p "what is your role and lens?"
> Я ревьювер кода, работающий через линзу безопасности (rev-sec) или архитектуры…
```

Определение `.claude/agents/reviewer.md` валидно и находится — разница только в способе выбора.

**Следствие для дизайна.** Роль — единственное, что нельзя передать через окружение, поэтому
она уезжает флагом `--agent`, а определения плагин раскладывает файлами в `~/.claude/agents/`
(§2.6). Через командную строку текст роли НЕ передаётся.

Отсюда требование к обёртке: она обязана пробрасывать `"$@"`. Если в ней написано `claude`
вместо `exec claude "$@"`, флаги `--agent` и `--permission-mode` до claude не дойдут, и агент
стартует безролевым и в manual mode. Проверка — `scripts/check-wrapper.sh`.

### 2.3 Настройки уровня проекта

`.claude/settings.json` в корне проекта имеет приоритет над `~/.claude/settings.json`.
Подтверждается строкой из бинарника:

> `This repository's settings set "crossSessionInbound" to "hold" (your own "accept" cannot override…)`

Значит `crossSessionInbound` задаётся **один раз на проект** и действует на все сессии в нём,
включая запущенные чужой обёрткой.

Но не всякий ключ так работает: `permissions.defaultMode` из проектных настроек Claude Code
**игнорирует** — см. §2.6. Проверяйте каждый ключ отдельно, общего правила нет.

Допустимые значения `crossSessionInbound`: `accept` / `hold` / `refuse` (проверено по
бинарнику; на одной из страниц документации ошибочно указаны `deliver`/`notice`).

### 2.4 Что нельзя задать без argv

- `--append-system-prompt` — env-аналога **не существует** (переменной
  `CLAUDE_CODE_APPEND_SYSTEM_PROMPT` в бинарнике нет, проверено).
- `--agent` — env-аналог есть, но не работает (§2.2.1).
- `--session-id` — env-аналог есть, но не работает (§2.2).
- `--permission-mode` — **тоже только argv**: `permissions.defaultMode` из настроек ПРОЕКТА
  Claude Code игнорирует (§2.6), а без режима агент стартует в manual mode.

То есть argv нужен ровно для двух вещей — **роль и режим прав**. Всё остальное закрывается
окружением, а `.claude/settings.json` проекта полезен только для `crossSessionInbound`.

### 2.5 Биллинг

На Team/Enterprise все параллельные сессии тянут из **одного посадочного лимита** (скользящее
5-часовое окно + недельное, общий с Claude chat и Cowork). Отдельного API-биллинга не
возникает: дочерний `claude` читает те же OAuth-креды из хранилища.

Два способа случайно уехать на API-биллинг:

- `ANTHROPIC_API_KEY` или `ANTHROPIC_AUTH_TOKEN` в окружении — плагин **обязан** вычищать их
  из env спавна, даже если сейчас их нет;
- флаг `--bare` — читает строго API-ключ, OAuth и keychain игнорирует, плюс не биндит
  inbox-сокет, из-за чего агент выпадает из `ListAgents`. Не использовать никогда.

Кэш на подписке живёт час (в ответе теста: `"ephemeral_1h_input_tokens": 6693`), но падает
до 5 минут, как только начинается расход usage credits.

### 2.6 Что выяснилось на живом прогоне

Раздел добавлен после первого запуска плагина в песочнице IDE. Всё ниже — не рассуждения,
а результаты, каждый из которых стоил отдельного цикла отладки.

**Терминал IDE запускает не тот шелл, что у процесса IDE.** В логе песочницы:
`Started WinConPtyProcess from [C:\Program Files\Git\usr\bin\bash.exe]`. То есть на Windows
во вкладке оказался Git Bash, а `ComSpec` указывал на cmd. Диалект надо брать из
`TerminalOptionsProvider.getShellPath()` самой IDE, а не из окружения процесса.

**Windows PowerShell не передаёт нативному exe аргумент, в котором есть и кавычки, и пробелы.**
Проверено последовательно:

| Попытка | Результат |
|---|---|
| `--agents '{"a":"b"}'` | `invalid JSON: Expected '}'` |
| то же с экранированием кавычек, значения без пробелов | работает |
| то же, но с пробелами внутри значений | `Unterminated string` |
| `--%` (stop-parsing token) | битый JSON |
| путь к файлу вместо JSON | `--agents` файлов не принимает |
| через `cmd /c` с экранированием | работает |
| `--agent <name>` — без кавычек и пробелов | работает |

**Терминал пишет в pty в кодировке JVM.** В песочнице это `windows-1251` (видно в JVM options
IDE), и кириллица, напечатанная в вкладку, приезжала кракозябрами. Значит через терминал нельзя
передавать ни русские промпты ролей, ни русские задачи.

**`executeCommand` рассчитан на шелл, а не на TUI.** Текст, напечатанный в уже поднявшийся
Claude Code, оседал в поле ввода неотправленным. Причина выяснилась позже (§2.7): в pty уходил
`\n`, а Enter в TUI — это `\r`. В новом терминале ввод дожимает сама платформа.

Три предыдущих факта вместе дают **главное правило проекта: в терминал печатается только ASCII,
и только команда запуска.** Роли уезжают файлами — `RoleInstaller` кладёт их в
`~/.claude/agents/`, и claude читает их сам как UTF-8; задачи уезжают через `SendMessage`.

Правило осталось в силе и после перехода на API 2026.2. Окружение теперь едет через API и
кодировки не касается, а Enter в TUI дожимает платформа — но **сама порча не-ASCII никуда не
делась**, это проверено живым прогоном на новом терминале (§2.7.1). Поэтому содержательный
канал по-прежнему один — межсессионные сообщения; печать осталась управляющим командам
(`/exit`, `/clear`), а `brief_agent` не-ASCII отклоняет.

**Наследуемые маркеры Claude Code ломают агента.** Если IDE запущена из терминала, который сам
живёт внутри сессии Claude Code, маркеры доезжают до агента по цепочке процессов. Агент
показывал `Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker` и **не
регистрировался в реестре** — снаружи это выглядело как «процесс есть, а в ListAgents его нет».
Опаснее всего `CLAUDE_CODE_MESSAGING_SOCKET` и `..._TOKEN`: это инбокс родительской сессии.

Вычищать надо **по префиксу, а не по списку имён**: список молча устареет с новой версией
Claude Code. Фактически утекает как минимум: `CLAUDECODE`, `CLAUDE_AGENTS_SELECT`,
`CLAUDE_CODE_ALT_SCREEN_FULL_REPAINT`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`,
`CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`,
`CLAUDE_CODE_SESSION_ID`, `CLAUDE_EFFORT`, `CLAUDE_JOB_DIR`, `CLAUDE_PID`.

**`permissions.defaultMode` из настроек ПРОЕКТА игнорируется.** Дословно из бинарника:

> `Maps to defaultMode: auto, which repo-level settings cannot grant in Claude Code (and the ignored value would shadow your user-level permission mode).`

Агент стартовал в manual mode и встал бы на первом же запросе прав в вкладке, которую никто не
читает. Режим задаётся только флагом `--permission-mode` либо пользовательскими настройками.

### 2.7 API переработанного терминала — проверено по jar-ам PyCharm 2026.2 (PY-262.9437.71)

Раздел заменяет прежние выводы про терминал: они были сняты с JediTerm-терминала, которого в
2026.2 уже нет как дефолта, и часть из них перестала быть верной.

**Классы лежат не там, где мы думали.** `TerminalToolWindowTabsManager` существует, но в
пакете `com.intellij.terminal.frontend.toolwindow`, а не `org.jetbrains.plugins.terminal`.
Прежний код искал его по старому имени, не находил и молча уезжал на legacy-путь. Модуль —
`intellij.terminal.frontend`, у него `visibility="public"`, поэтому зависимость на него можно
и нужно объявить в `plugin.xml`: без этого classloader плагина классы модуля не видит.

**Что даёт билдер вкладки** (`createTabBuilder()`):
`tabName`, `workingDirectory`, **`envVariables(Map)`**, `shellCommand(List)`, `requestFocus`,
`deferSessionStartUntilUiShown`, `closeOnProcessTermination`, `contentManager`,
`shouldAddToToolWindow`, `createTab()`.

Отсюда главное следствие: **переменные окружения больше не надо вписывать в командную строку.**
Вместе с этим ушли экранирование, кавычки и вся история про «PowerShell не передаёт нативному
exe аргумент с кавычками и пробелами». В строке остаётся только то, что окружением задать
нельзя, — роль и режим прав.

**Что даёт вкладка**: `getView()` → `com.intellij.terminal.frontend.view.TerminalView` с
`createSendTextBuilder()`, `sendText`, `getOutputModels()`, `getSessionState()` (NotStarted /
Running / Terminated), `getStartupOptionsDeferred()`, `hasChildProcesses()`, `getTitle()`.

**`TerminalSendTextBuilder` закрывает старую проблему с TUI.** У него есть `shouldExecute()`
и `useBracketedPasteMode()`. Прежний вывод «`executeCommand` рассчитан на шелл, а не на TUI,
текст оседает в поле ввода неотправленным» объяснялся тем, что в pty уходил `\n`, а Enter в
TUI — это `\r`. Теперь дожатие ввода делает платформа, поэтому `/exit` и `/clear` доезжают
до поднявшегося Claude Code — а на них держатся `close_agent` и `reset_agent`, которые до
этого молча не работали.

**`startupOptionsDeferred` отдаёт `pid` шелла и его командную строку.** Это авторитетный
источник и для сопоставления вкладки с сессией по дереву процессов, и для выбора диалекта
шелла: не настройка IDE и не окружение процесса IDE, а то, что реально запущено во вкладке.

**Editor area — штатная операция.** `TerminalInEditorSupport.openInEditor(content, editorWindow)`
(реализация платформенного `ToolWindowInEditorSupport`) — то же самое, что делает пункт меню
Move to Editor. Свой `FileEditorProvider` писать не нужно.

#### 2.7.1 Живой прогон на новом терминале — что подтвердилось и что нет

Прогон в песочнице 2026.2, управление шло по HTTP через MCP-сервер плагина, то есть теми же
вызовами, что делает оркестратор.

Подтвердилось: вкладка создаётся, `envVariables` доезжают (имя сессии оказалось в реестре,
модель — в шапке TUI), роль применяется флагом (`@mjc-researcher`), режим прав применяется
(`auto mode on`), `read_tab` читает экран через `activeOutputModel`, а **`/exit` доходит до
поднявшегося TUI** — запись из реестра исчезла, вкладка закрылась. Именно на этом держатся
`close_agent` и `reset_agent`, и до перехода на `shouldExecute()` они молча не работали.

**Кириллица в терминал по-прежнему едет битой — и это не лечится bracketed paste.** Отправили
`Ответь ровно одним словом: ПРОБА-OK`, в TUI приехало `❯ ������ ����� ����� ������: �����-OK`,
и агент ответил на выдуманный текст. Ответ самого агента при этом отрисовался кириллицей
верно, то есть портится не отображение, а байты, которые IDE пишет в pty: не UTF-8, тогда как
Claude Code читает stdin как UTF-8. Правило §2.6 «в терминал только ASCII» остаётся в силе,
а `brief_agent` теперь такой текст **отклоняет**: молчаливое искажение выглядит как
выполненная команда.

**Флаг `--agent` перебивает `CLAUDE_CODE_AGENT` в реестре.** При запуске с
`CLAUDE_CODE_AGENT=researcher --agent mjc-researcher` в записи оказалось
`"agent":"mjc-researcher"`. Значит поле реестра содержит то, что реально применилось, и
разбирать его надо с учётом префикса `mjc-`.

**`getTabs()` не показывает вкладки, унесённые в editor area.** После Move to Editor вкладка
исчезает из списка менеджера вкладок целиком, и плагин переставал видеть её вовсе: не находил
родителя, не мог ни прочитать её экран, ни закрыть. То есть искали мы везде, кроме места, где
оркестратор живёт по дизайну. Терминал в редакторе — это открытый `TerminalViewVirtualFile` с
публичным `getTerminalView()`, поэтому перечислять надо оба источника: вкладки тулвиндоу плюс
открытые файлы этого типа. Закрывается такой терминал тоже иначе — как файл, а не через
`closeTab`.

**Открытие вкладки в editor area уводит выделение на неё.** Спавн агента переключал
разработчика с вкладки оркестратора — той единственной, за которой он наблюдает. Поэтому после
размещения выбор возвращается на прежнюю вкладку окна.

**Реестр надо читать устойчиво к BOM.** Файл сессии, который не распарсился, — это невидимый
агент: он есть в системе, но его нет ни в `ListAgents`, ни для плагина. Поймано автотестом:
PowerShell писал запись через `Set-Content -Encoding utf8`, то есть с BOM, и наш JSON на нём
спотыкался. Разбирать такую пропажу вживую было бы крайне неприятно.

**Editor area в тестах не существует.** Платформа подставляет `TestEditorManagerImpl`, у
которого нет ни одного окна редактора (замер: `окон=0` при одном открытом файле) — и в лёгкой
фикстуре, и в тяжёлой. Поэтому размещение агента рядом с оркестратором автотестом не
проверяется в принципе; автоматически проверяется только то, что его отсутствие не мешает
агенту подняться.

**Состояние UI нельзя читать вне EDT.** Диагностика перечисляла вкладки и спрашивала активный
редактор прямо на потоке HTTP-запроса, и `currentWindow` там пустой — на экране был открытый
терминал, а диагностика показывала «активной вкладки нет». Все чтения ушли в `runOnEdt`.

### 2.8 Что в итоге печатается в терминал

Одна короткая строка, только ASCII:

```sh
claude --agent mjc-researcher --permission-mode auto
```

Всё остальное уехало в `envVariables` вкладки:

| Часть | Где | Зачем |
|---|---|---|
| `CLAUDE_CODE_SESSION_NAME` | env вкладки | имя = адрес для `SendMessage` |
| `ANTHROPIC_MODEL` | env вкладки | иначе ресерчер поедет на модели оркестратора |
| `CLAUDE_CODE_AGENT` | env вкладки | только метка в реестре, роль не задаёт (§2.2.1) |
| `MJC_REPORTS_DIR` | env вкладки | куда агенты кладут развёрнутые отчёты (вне репозитория) |
| `--agent` + `--permission-mode` | командная строка | роль из файла и режим прав, оба только argv |

Перед командой печатается снятие унаследованных маркеров, если они реально есть в окружении
IDE (`unset CLAUDECODE CLAUDE_CODE_MESSAGING_SOCKET …`). Имена берутся из окружения самой
IDE, а не из зашитого списка: агент наследует именно его, значит вычистить надо ровно то, что
там лежит, и список не может устареть с новой версией Claude Code.

Почему нельзя вычистить через `envVariables`: она умеет только задать значение, а нам нужно
отсутствие переменной. Пустая строка не годится — Claude Code часть маркеров проверяет на
`undefined`, а не на пустоту (в бинарнике 2.1.251: `r === void 0 ? [] : …` для
`CLAUDE_CODE_MESSAGING_SOCKET`), и агент принял бы инбокс родителя за свой.

## 3. Архитектура


```
┌─ JetBrains IDE ─────────────────────────────────────────────────┐
│                                                                 │
│  EditorWindow A            │  EditorWindow A' (split справа)    │
│  ┌───────────────────────┐ │  ┌──────────────────────────────┐  │
│  │ mjc-orc               │ │  │ mjc-impl-be                  │  │
│  │ ── ты пишешь сюда ──  │ │  ├──────────────────────────────┤  │
│  │                       │ │  │ mjc-rsrch                    │  │
│  └───────────┬───────────┘ │  └──────────────────────────────┘  │
│              │ MCP                        ▲                     │
│              ▼                            │ sendText            │
│      ┌───────────────────┐                │                     │
│      │  MetaJetCore      │────────────────┘                     │
│      │  plugin (Kotlin)  │  spawn / close / reset / focus       │
│      └───────────────────┘                                      │
└─────────────────────────────────────────────────────────────────┘
        mjc-orc ⇄ mjc-impl-be — cross-session messaging (named pipe / uds)
```

Три канала, у каждого своя роль:

| Канал | Направление | Для чего |
|---|---|---|
| MCP | оркестратор → плагин | управление вкладками: спавн, закрытие, сброс, фокус |
| cross-session messaging | агент ⇄ агент | вся содержательная переписка |
| `TerminalView.sendText()` | плагин → любая вкладка | стартовый брифинг; аварийное «агент завис» |

Третий канал нужен вот почему: сообщение от агента **никогда** не считается согласием
пользователя, поэтому оркестратор не может подтвердить чужой пермишен-промпт. Если агент
всё-таки упрётся, плагин увидит это по `status` в реестре и впечатает строку в терминал
оркестратора. Использовать экономно — каждая инъекция это полноценный ход с полным контекстом.

## 4. Протокол спавна

Плагин **имитирует ручной запуск**: открывает вкладку, печатает пользовательскую команду
запуска, дожидается готовности, печатает брифинг.

### 4.1 Последовательность

```
1. Плагин генерит имя:  mjc-impl-be

2. Создаёт вкладку через createTabBuilder(), передавая окружение по API:
       CLAUDE_CODE_SESSION_NAME = mjc-impl-be
       ANTHROPIC_MODEL          = opus
       CLAUDE_CODE_AGENT        = implementer   (только метка в реестре, роль не задаёт)
       MJC_REPORTS_DIR          = ~/.claude/metajetcore/<проект>/reports

3. Если вкладка родителя живёт в editor area — открывает новую рядом с ней
   (TerminalInEditorSupport.openInEditor), иначе оставляет в тулвиндоу.

4. Ждёт, пока sessionState вкладки станет Running: до этого печатать некуда.

5. Печатает команду запуска — только ASCII:
       [unset унаследованных маркеров; ]<launchCommand> --agent mjc-implementer --permission-mode auto

6. Ждёт появления записи в ~/.claude/sessions/*.json с name == mjc-impl-be.
       Оттуда берёт pid, sessionId и фактическое имя.

7. Возвращает оркестратору имя и текст задачи с указанием отправить её SendMessage.
```

**Почему шаг 4 по реестру, а не по таймеру.** Обёртка может занимать произвольное время,
а появление записи означает, что `claude` реально поднялся и уже забиндил inbox-сокет,
то есть готов и к вводу, и к сообщениям. Таймер здесь будет флаковать.

### 4.2 Настройки плагина

| Настройка | По умолчанию | Назначение |
|---|---|---|
| Launch command | `claude` | сюда пользователь вписывает свою обёртку |
| Permission mode | `auto` | флаг `--permission-mode`; пусто — не добавлять |
| Name prefix | аббревиатура проекта (`MetaJetCore` → `mjc`) | префикс имён сессий |
| Ready timeout | 45 s | сколько ждать появления записи в реестре |
| Strip API keys | `true` | снимать `ANTHROPIC_*` |
| Strip Claude markers | `true` | снимать унаследованные `CLAUDE*` |
| Env overrides | пусто | дополнительные переменные, `KEY=VALUE` построчно |
| MCP port | `0` | 0 — вывести из пути проекта, чтобы порт был стабильным |

Настройки диалекта шелла нет: он определяется по фактическому процессу вкладки (§2.7).
Настроек передачи роли тоже нет — режим один, флагом `--agent` (§2.2.1).

## 5. Роли

Ровно четыре. Больше не нужно: узкое место — не параллелизм, а контекст.

| Роль | Имя | Как включается | Модель | Инструменты | Сколько |
|---|---|---|---|---|---|
| Оркестратор | `<pfx>-orc` | **скилл `/orchestrate`** | Opus | чтение + мессаджинг, запрет на запись промптом | 1 на задачу |
| Имплементер | `<pfx>-impl-be`, `-fe` | флаг от плагина | Opus | полные | 1; второй только при явном разделении fe/be |
| Ресерчер | `<pfx>-rsrch` | флаг от плагина | Sonnet | только чтение | 1 |
| Ревьювер | `<pfx>-rev-sec`, `-rev-arch` | флаг от плагина | Sonnet | только чтение | 0–2, **после** имплементера |

### 5.0 Оркестратор — скилл, агенты — флаг

Роли включаются двумя разными способами, и это осознанная асимметрия.

**Оркестратор — скилл `/orchestrate`** в пользовательском скоупе (`~/.claude/skills/`,
ставится плагином). Обычные сессии Claude Code остаются обычными: оркестратор включается по
требованию, а не отдельным способом запуска. Побочные выгоды:

- скилл можно вызвать **посреди разговора**, когда контекст задачи уже набран — оркестратор
  стартует не с нуля;
- пользовательский скоуп значит «доступно во всех проектах сразу», в целевой проект
  копировать нечего;
- не зависит от того, пробрасывает ли обёртка `"$@"` — в отличие от `--agent`.

Про ограничение инструментов — уточнение после проверки схемы фронтматтера Claude Code 2.1.251
(снята из бинарника). Поля есть, и не одно:

```
name, description, model, allowed-tools, disallowed-tools, argument-hint,
disable-model-invocation, user-invocable, effort, shell, version,
when_to_use, paths, hooks, context (inline|fork), agent, background
```

`allowed-tools` — «Tools available to the model while this file is active»,
`disallowed-tools` — «Tools removed from the model while this file is active. **Cleared when
the user sends the next message**». Мы ставим `disallowed-tools: Edit, Write, NotebookEdit`,
но именно из-за последней оговорки это не гарантия уровня дочерних агентов: ограничение живёт
до следующей реплики разработчика, а не всю сессию. Настоящий запрет на запись у оркестратора
держится промптом, и это приемлемо именно для него — **это та вкладка, за которой разработчик
наблюдает**: если он начнёт писать код, это видно сразу.

**Дочерние агенты — флагом** `--agents '<json>' --agent <role>` от плагина, с жёстким
ограничением `tools`. Они работают в ненаблюдаемых вкладках, там гарантия нужна настоящая,
а не промптовая.

### 5.1 Оркестратор: чтение — да, запись — нет

Решение по спорному вопросу.

Сверить одно утверждение ресерчера — это один `Read` в контексте оркестратора. Отправить тот
же вопрос ресерчеру — это полный ход в **двух** сессиях: сообщение доставляется простаивающей
сессии как новый ход с её полным контекстом, ответ возвращается так же. Точечная сверка через
`Read` строго дешевле.

Риск не в наличии инструмента, а в соблазне *исследовать*. Поэтому в промпт роли зашито
правило: **больше трёх файлов подряд — это задача для ресерчера, а не для тебя.**

Запись запрещена, чтобы оркестратор физически не мог начать делать работу имплементера сам —
типичный сбой лида в подобных схемах.

### 5.2 Ревьюверы — после, не параллельно

Ревьюить недописанное — это шум и сожжённые токены. Момент ревью определяет оркестратор:
целиком или по готовым кускам. Два ревьювера имеют смысл только с разными линзами
(`rev-sec` — безопасность, `rev-arch` — архитектура и производительность). Различаются они
именно линзой, а не номером: `rev-1` и `rev-2` становятся неразличимы через полчаса работы.

## 6. Нейминг

Имена сессий **глобальны на машину**, а параллельно живут несколько проектов. Разрешены
только буквы, цифры, дефисы и подчёркивания — иначе `@`-mention придётся брать в кавычки.

```
<префикс проекта>-<роль>[-<домен>]

mjc-orc     mjc-impl-be     mjc-impl-fe
mjc-rsrch   mjc-rev-sec     mjc-rev-arch
```

Заголовок вкладки в IDE = имя сессии, один в один.

При коллизии имён Claude Code сам переименует новую сессию в вариант, оставив имя за той,
что заняла его первой. Поэтому плагин перечитывает реестр и берёт **фактическое** имя
оттуда, а не то, которое запрашивал.

## 7. Компоновка окон

Рабочий сценарий: 3–4 задачи параллельно, у каждой свой оркестратор в своей четверти экрана.
Агент должен появляться **рядом со своим оркестратором**, а не в общей куче.

### 7.1 Почему editor area, а не Terminal tool window

Прежний довод — «в тулвиндоу нет публичного API для сплита» — в 2026.2 неверен: терминал
регистрирует `toolWindow.splitContentProvider`, то есть сплит вкладок тулвиндоу стал штатным.
Причина осталась одна, зато настоящая: **вертикального места в editor area кратно больше**, и
разработчик всё равно держит сессии там.

Агент открывается **соседней вкладкой в окне оркестратора, а не сплитом**. Сплит на каждого
агента нагляднее ровно до третьей роли, после чего окно превращается в набор узких полосок;
разделить его пополам разработчик всегда может сам. Группировка от этого не страдает: агенты
лежат в том же окне, что их оркестратор, а не в общей куче.

Перенос — платформенной операцией, той же, что пункт меню Move to Editor:

```kotlin
// content вкладки терминала + окно, в котором его показать
TerminalInEditorSupport().openInEditor(tab.content, editorWindow)

// окно родителя, чтобы агент оказался рядом
val fem = FileEditorManagerEx.getInstanceEx(project)
val parentWindow = fem.windows.first { it.fileList.contains(parentFile) }
```

Свой `FileEditorProvider` писать не нужно: у плагина терминала он уже есть.

Зависимости в `plugin.xml` — плагин терминала и его модуль `intellij.terminal.frontend`
(§2.7): без второй строки classloader не видит классы нового API.

### 7.2 Как плагин находит родителя

Оркестратор передаёт своё имя в вызов `spawn_agent(parent = "mjc-orc", …)`. Своё имя он
знает: **первая строка вывода `ListAgents` — это имя текущей сессии.**

Плагин сопоставляет имя с вкладкой тремя путями, по убыванию надёжности:

1. **Основной** — вкладки, созданные плагином (`spawn_agent`, «New Orchestrator Here»), лежат
   в карте `имя → вкладка`.
2. **По дереву процессов** — для сессий, запущенных руками: `startupOptionsDeferred.pid` даёт
   pid шелла вкладки, `pid` из реестра — процесс `claude`; если шелл среди его предков, сессия
   живёт здесь.
3. **По заголовку вкладки** — последняя попытка.

Действие **New Orchestrator Here** не просто удобство: оно сразу переносит вкладку в editor
area, и только тогда «открыть агента рядом» вообще имеет смысл. У вкладки в тулвиндоу
соседства нет.

## 8. Жизненный цикл и управление

| Операция | Как | Когда применять |
|---|---|---|
| `spawn_agent(role, parent, task, …)` | см. §4 | нужна новая роль в задаче |
| `brief_agent(name, text)` | вставка текста прямо во вкладку | аварийно: агент не отвечает на сообщения |
| `reset_agent(name)` | печатает `/clear` | **этап закрыт, контекст больше не нужен** |
| `close_agent(name)` | `/exit`, дождаться исчезновения из реестра, закрыть вкладку | роль отработала |
| `focus_agent(name)` | показать вкладку разработчику | нужно, чтобы человек посмотрел |
| `read_tab(name)` | хвост экрана вкладки | агент поднялся, но молчит |
| `list_agents()` | чтение реестра с фильтром по `cwd` | статус всех агентов |

`restart_agent` пока не реализован — при необходимости это `close_agent` + `spawn_agent`.

Записи мёртвых процессов из реестра отфильтровываются по `pid`: файл удаляет сама сессия при
выходе, поэтому после падения он остаётся, и без проверки такой призрак и в `list_agents`
выглядит живым, и навсегда занимает имя — а имена глобальны на машину.

`reset_agent` важнее, чем кажется: между этапами дешевле сбросить контекст имплементера, чем
тащить историю предыдущего этапа в каждый следующий ход. Но **внутри** этапа контекст
сохраняется — в этом весь смысл схемы (см. §1.1).

Закрытие только через `/exit`, не через kill процесса: иначе останется запись в реестре и
мёртвый пайп, и `ListAgents` будет показывать призрака.

## 9. Экономика

Три факта, которые вместе дают неприятный эффект:

1. Сообщение доставляется простаивающей сессии **как новый ход с полным контекстом**.
   Переписка стоит дорого с обеих сторон.
2. Каждый агент держит свой контекст. Документация по agent teams даёт ориентир **~7×**
   к одиночной сессии.
3. Кэш живёт час на подписке и 5 минут на usage credits.

Правила, зашитые в определения ролей:

- **Ответ — в сообщении, не больше пяти строк.** Выгружать длинный текст в файл смысла нет:
  оркестратору всё равно пришлось бы его прочитать, а read-only роли ради этого обходили бы
  запрет через `Bash` — на живом прогоне ресерчер так и сделал и упёрся в длину команды.
- **`notify_when_idle` вместо «ну как там?».** Подписка не запускает ход у наблюдаемой
  сессии и не стоит ей ничего.
- **Батчить.** Одно сообщение вместо трёх. Платформа и сама дропает одинаковые повторы и
  троттлит петли: очередь 50 сообщений, кап около 1M символов на сообщение.
- **Асимметрия моделей.** Opus только там, где пишут код. Поиск и вычитка — Sonnet.
- **Оркестратору не нужен 1M-контекст.** Он диспетчер. Если его контекст дорос до
  автокомпакта — схема сломана: он читает то, что должен читать ресерчер.

## 10. Авто-режим

Все сессии работают в auto mode. Следствия:

- auto относится к классу «prompting», а не «bypassing». Обе стороны в одном классе →
  сообщения доставляются **без диалога подтверждения**. Это нужный режим.
- Классификатор auto mode дополнительно просматривает входящие межагентные сообщения и
  может заблокировать доставку. Чтобы поведение было детерминированным,
  `crossSessionInbound: "accept"` ставится явно в `.claude/settings.json` проекта.
- Подтвердить чужой пермишен-промпт оркестратор не может и не должен — это защита от
  permission laundering. Обработка зависшего агента — через канал `sendText` (§3).

## 11. Порядок работ

Сначала то, что может убить идею, потом код.

1. **Промптинг — 30–40 минут, без единой строки кода.** Три вкладки руками с нужными env,
   реальная задача оркестратору. Проверяется единственное, что ничем не гарантировано:
   удержатся ли агенты от того, чтобы спросить человека вместо оркестратора. Замерить
   `/usage` до и после — получить цену одного цикла.
2. **Проверить, что `CLAUDE_CODE_AGENT` действительно выбирает определение роли**, а не
   только пишется в реестр. Одна сессия, один вопрос «кто ты».
3. **Встроенный MCP-сервер JetBrains** (`Settings | Tools | MCP Server`, бандлится с 2025.2+,
   сейчас выключен). Если его `execute_terminal_command` с `reuseExistingTerminalWindow=false`
   открывает вкладку и не блокируется на долгоживущем процессе — часть работы плагина
   отпадает. Сплит в нужную панель он не даст, но для шага 1 сгодится как времянка.
4. **Плагин**: `spawn` / `close` / `reset` / `list` + `openInRightSplit`. Ничего больше.
5. Обвязка: хуки, мониторинг статусов, восстановление раскладки.

## 12. Перенос в существующий проект

**С установленным плагином переносить не нужно ничего.** И скилл оркестратора
(`~/.claude/skills/orchestrate/`, §5.0), и определения ролей (`~/.claude/agents/mjc-*.md`)
живут в пользовательском скоупе — плагин их туда кладёт сам при старте IDE. В целевом проекте
нужен один ключ в `.claude/settings.json`:

```json
{ "crossSessionInbound": "accept" }
```

`permissions.defaultMode` в проектных настройках задавать бесполезно — Claude Code его
игнорирует (§2.6), режим прав передаёт плагин флагом.

Остальная часть раздела — про ручной режим (шаг 1, до плагина) и про то, что вообще лежит
в `.claude/`, если захочется разложить роли файлами.

> После установки плагина **удалите из проекта копию скилла** `.claude/skills/orchestrate/`:
> плагин ставит свою в пользовательский скоуп и обновляет её при каждом старте IDE, а две
> копии разъедутся по версиям.

### 12.0 Субагентов в этой архитектуре нет

Все четыре роли — **полноценные отдельные сессии** Claude Code, каждая в своей вкладке, со
своим процессом, своим контекстом и своим адресом для `SendMessage`. Инструмент `Agent`
и субагенты в схеме не участвуют нигде (почему — §1.1).

Ниже субагенты упоминаются ровно по одной причине: папка `.claude/agents/` в Claude Code
обслуживает **два несвязанных применения**, и от второго нельзя отписаться. Это побочный
эффект хранилища, а не элемент дизайна.

### 12.1 Что такое `.claude/agents/`

Стандартная папка **определений агентов**. Один файл — одно определение:

```markdown
---
name: implementer          # имя определения
description: …             # по нему Claude решает, когда делегировать
tools: Read, Edit, Bash…   # белый список инструментов
model: opus
---
Тело файла = системный промпт агента.
```

У определения два независимых применения:

1. **Тип субагента.** Claude в этом проекте сможет делегировать задачу через `Agent` с
   `subagent_type: implementer`. Это происходит **автоматически**, просто потому что файл
   лежит в папке.
2. **Роль целой сессии** — `claude --agent implementer`. Именно так мы их и используем:
   тело становится системным промптом сессии, `tools` ограничивает набор инструментов,
   `model` задаёт модель.

Мы используем **только применение 2**. Применение 1 нам не нужно и не используется.

> **Побочный эффект при переносе.** Отписаться от применения 1 нельзя: как только файлы
> окажутся в существующем проекте, четыре новых типа субагентов появятся в списке доступных,
> и основная сессия может начать сама делегировать в `implementer` или `reviewer`. Смягчается
> полем `description` (у наших определений оно начинается с «НЕ использовать как субагента» —
> Claude выбирает субагента именно по описанию), но полностью проблему снимает только §12.1.1.

#### 12.1.1 Определения инлайном — способ вообще не трогать проект

Роль можно передать при запуске, без единого файла в проекте:

```bash
claude --agents '{"implementer":{"description":"…","prompt":"…",
                  "tools":["Read","Grep","Edit","Write","Bash"],"model":"opus"}}' \
       --agent implementer
```

Проверено: системный промпт применяется, `tools` ограничивают набор инструментов, `model`
задаёт модель, и в `.claude/agents/` при этом не появляется ничего. Контрольный зонд с
`"tools":["Read","Grep"]` ответил `PROBE-OK: … I have Read and Grep tools but no Edit or Write`.

**Этот режим был выброшен, и вот почему.** Инлайновый JSON — это argv, а под Windows
PowerShell аргумент с кавычками и пробелами до нативного exe не доезжает вовсе; плюс
промпты ролей на русском, а терминал писал в pty в кодировке JVM (§2.6). Плагин вместо этого
раскладывает определения файлами в **пользовательский** скоуп `~/.claude/agents/mjc-*.md`:
проект остаётся чистым ровно так же, а текст роли claude читает сам как UTF-8.

Побочный эффект применения 1 при этом остаётся, но в пользовательском скоупе он безобиднее:
типы субагентов `mjc-*` видны во всех проектах, и от делегирования в них удерживает описание
(«НЕ использовать как субагента»).

Ограничение общее с `--agent`: это argv, нужна обёртка с `"$@"`.

### 12.2 Что с чем сливать

| Из этого проекта | В существующем проекте | Как переносить |
|---|---|---|
| `.claude/agents/*.md` | может не быть | скопировать; при совпадении имён — переименовать наши |
| `.claude/settings.json` | **часто уже есть** | **слить ключи, не перезаписывать файл** |
| `.claude/skills/orchestrate/` | может не быть | скопировать целиком |
| `scripts/spawn-agent.sh` | может быть свой `scripts/` | скопировать, при конфликте переименовать |
| `docs/ARCHITECTURE.md`, `PLUGIN-SPEC.md` | почти наверняка занято | положить в `docs/meta-orchestrator/` |

Из `settings.json` нужны ровно два ключа. Добавить их к существующим, сохранив всё остальное:

```json
{
  "crossSessionInbound": "accept",
  "permissions": { "defaultMode": "auto" }
}
```

Если в проекте уже есть блок `permissions` с `allow`/`deny` — добавить `defaultMode` внутрь
него, не заменяя блок целиком.

### 12.3 Что поправить руками после копирования

- **Префикс имён.** `mjc-` меняется на аббревиатуру нового проекта: имена сессий глобальны
  на машину, и два проекта с одинаковым префиксом начнут путаться.
- **Файловые домены.** В определении имплементера домен приходит из брифинга, но если в
  проекте есть зоны, куда агентам нельзя, — проще всего закрыть их через `permissions.deny`
  в настройках проекта, это подействует на все сессии.

## 13. Открытые вопросы

- Четыре оркестратора — это четыре окна IDE или четыре сплита в одном проекте? От этого
  зависит, живёт карта вкладок в `Project`-скоупе или в `Application`-скоупе.
- Нужен ли плагину свой tool window со списком агентов, или достаточно заголовков вкладок.
- Восстановление раскладки после рестарта IDE: `sessionId` известен, но `--resume` — флаг,
  который обёртка может съесть. Вероятный путь — печатать `/resume <id>` уже в поднятой
  сессии.
- Целевая ОС для сборки — Linux. Все проверки выше сделаны на Windows; транспорт там
  именованные пайпы, на Linux — unix-сокеты. Логика реестра идентична, но путь сокета в
  `messagingSocketPath` выглядит иначе.
- Остаётся непроверенным живьём: работает ли `openInEditor` для только что созданной вкладки
  и попадает ли агент рядом с родителем (в прогоне родитель был не в editor area);
  сопоставление вкладки по дереву процессов для оркестратора, запущенного руками;
  снимается ли `disallowed-tools` скилла со следующей репликой разработчика.
- Можно ли вообще заставить IDE писать в pty в UTF-8 (§2.7.1). Если да — `brief_agent`
  перестанет быть аварийным каналом, но на схему это не влияет: содержательный канал всё
  равно межсессионный.
- Что делать, если разработчик переключил движок терминала на Classic: плагин перейдёт в
  ручной режим (API нового терминала не найдётся). Возможно, стоит явно сказать об этом
  уведомлением, а не только в диагностике.
