# Задача для моста Claudiki: связь «агент → оркестратор» по `sessionId`

Документ описывает правку **на стороне моста** (`~/claudiki/bridge`). Со стороны
MetaJetCore всё уже сделано — см. «Что приезжает от плагина».

---

## Зачем

Сейчас команда собирается сравнением **имён**: агент привозит `MJC_PARENT` с именем своего
оркестратора, мост ищет сессию с таким `reg_name`.

Имя для этого не годится, и дело не в аккуратности реализации:

- **имя не уникально.** Замер на живом стенде: три записи реестра одновременно назывались
  «слитие мастера». Двум разным оркестраторам ничто не мешает называться одинаково —
  имя задаёт человек;
- **имя меняется.** `/rename` посреди работы переименовывает сессию, и все её агенты
  мгновенно теряют родителя;
- **имя переиспользуется.** Оркестратор умер, имя занял новый имплементер — протухший
  `MJC_PARENT` указывает уже на него. От этого в мосту уже стоит отдельная заплатка
  (`test_agent_named_as_parent_does_not_become_orchestrator`), и она нужна ровно потому,
  что ключ плохой.

`sessionId` свободен от всех трёх: он уникален, не меняется и переживает resume — у тех трёх
записей «слитие мастера» `sessionId` был один и тот же (`0ba88519-…`).

И главное: `sessionId` мост **уже знает** — это `session_id` из конверта хука, он же ключ
`Bridge.sessions`. То есть сопоставление сводится к прямому обращению по ключу вместо
сравнения строк.

---

## Что приезжает от плагина

Начиная с этой версии MetaJetCore вкладке агента ставятся **две** переменные:

| Переменная | Что в ней | Роль |
|---|---|---|
| `MJC_PARENT_SESSION` | `sessionId` оркестратора | **ключ связи** |
| `MJC_PARENT` | имя оркестратора | справочно, для человека и старых получателей |

Как плагин получает `sessionId` (для понимания гарантий):

1. Основной путь — запись реестра, по которой нашлась **вкладка** родителя. Она найдена
   сопоставлением pid: pid из записи ведёт к процессу `claude`, тот — к шеллу вкладки. Это
   единственный способ развести тёзок, и он привязан к конкретному процессу.
2. Запасной — реестр по имени, **только если ответ однозначен**: все записи с этим именем
   дают один `sessionId` (случай resume).
3. Если однозначно не вышло — **переменной нет вовсе**.

Отсюда правило для моста:

> **Отсутствие `MJC_PARENT_SESSION` при наличии `MJC_PARENT` — это «связь неизвестна»,
> а не «свяжи по имени».** Плагин не смог определить родителя однозначно; достраивание по
> имени вернёт ровно ту ошибку, ради которой всё это делается — чужая команда на экране.

Ограничения на значение: непустая строка, обычный UUID Claude Code. Обрезки по длине нет
(в отличие от `MJC_PARENT`, который режется до 64 символов).

## Правки

### 1. `bridge/octo-notify.py` — привезти переменную

В цикле, который перекладывает окружение в payload, добавить пару:

```python
for key, env in (("agent", "CLAUDE_CODE_AGENT"),
                 ("sess_name", "CLAUDE_CODE_SESSION_NAME"),
                 ("parent", "MJC_PARENT"),
                 ("parent_sid", "MJC_PARENT_SESSION")):
```

Обрезка `val[:64]` для `parent_sid` мала — UUID длиннее. Либо поднять лимит для этого ключа,
либо резать по 64 только `parent`/`sess_name`/`agent`.

### 2. `bridge/bridge.py` — поле в `Session`

Рядом с `parent`:

```python
parent: str = ""          # имя оркестратора (MJC_PARENT) — справочно
parent_sid: str = ""      # session_id оркестратора (MJC_PARENT_SESSION) — ключ связи
```

### 3. `bridge/bridge.py` — приём события

Там же, где сейчас читается `hook_parent`:

```python
hook_parent     = str(data.get("parent") or "")[:64]
hook_parent_sid = str(data.get("parent_sid") or "")[:64]
```

и присваивание для уже известной сессии — рядом с `sess.parent = hook_parent`:

```python
if hook_parent_sid:
    sess.parent_sid = hook_parent_sid
```

плюс `parent_sid=hook_parent_sid` во все три конструктора `Session(...)` (ветки `start`,
`working`, общий путь) — по образцу `parent=hook_parent`.

### 4. `bridge/bridge.py` — `teams()`

Порядок сопоставления, от точного к приблизительному:

1. **`parent_sid`** — прямое обращение: `self.sessions.get(s.parent_sid)`, точнее — поиск
   среди `sessions`, переданных в `teams()`, по `session_id`. Совпало → агент этой команды,
   дальше не смотрим.
2. **`parent`** (имя) — текущая логика через `name_key`. Остаётся для агентов, поднятых
   плагином прошлой версии.
3. **префикс имени** — текущая эвристика, для агентов, запущенных руками.

Что при этом меняется в существующих правилах:

- **Оркестратором становится и тот, на чей `session_id` сослались.** Сейчас список `orcs`
  собирается из сессий, чьё `reg_name` кто-то назвал родителем. Надо добавить: сессия, на
  чей `session_id` сослались через `parent_sid`, — тоже оркестратор. Это по-прежнему
  единственный способ узнать сессию, включившую `/orchestrate`: скилл не меняет ни имени, ни
  окружения, ни реестра.
- **Проверка «родитель не должен сам быть агентом» для sid-пути не нужна.** Она защищала от
  переиспользования имени; `session_id` не переиспользуется. Но по имени она обязана
  остаться — путь 2 никуда не делся.
- **Родитель назван, но его нет на глазах — агент не прилипает к чужой команде.** Правило
  сохраняется и для `parent_sid`: не нашли сессию с таким `session_id` → агент остаётся
  своей карточкой, к эвристике по префиксу **не** скатываемся.

### 5. `CLAUDE.md` моста

Абзац про мета-оркестрацию сейчас говорит «точной связи родитель→агент нигде нет» и
описывает эвристику по префиксу. Его надо переписать: связь есть, ключ — `sessionId`,
имя оставлено справочно.

## Совместимость

Правка **аддитивная**. Агенты, поднятые плагином прошлой версии, `parent_sid` не привозят и
собираются по имени, как сейчас. Обновление плагина и моста можно катить в любом порядке:

- новый плагин + старый мост — мост просто игнорирует лишний ключ payload;
- старый плагин + новый мост — `parent_sid` пуст, работает путь по имени.

Уже запущенные агенты `parent_sid` не получат никогда: переменные окружения живого процесса
не переписать. Дерево по `sessionId` соберётся для тех, кого заведёт обновлённый плагин.
