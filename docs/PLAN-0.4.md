# MetaJetCore 0.4 — план работ

**Дата:** 2026-11-04
**Цель:** стабильная работа окон на IDE 2026.3+, разнородная команда (Claude Code + Codex),
роли под tempo, максимум возможностей IDE.

Порядок жёсткий: этапы идут по очереди, каждый доводится до конца (сборка, тесты фичи, живая
проверка) и только потом начинается следующий. Решения, принятые с разработчиком, — в §0;
факты, на которые план опирается, — в §1. Всё, что ещё не проверено, вынесено в эксперименты
(§7) и стоит в начале того этапа, которому оно нужно.

## 1. Что установлено исследованием

### 1.1 Терминал: 2026.2 (262.11879) против 2026.3 (263.6949) — по jar-ам

Ядро API совместимо. Отличия билдера вкладки в 263: появились `emulatorType`, `userDefinedName`,
`restoreOnProjectReopen`, `pendingContent`, `sourceNavigationProjectResolver`; пропал
`sourceNavigationProjectPath`. В `TerminalView`: `addInputInterceptor` → `addKeyEventsListener`
(мы не используем). `openInEditor` в 263 сначала достраивает «отложенную» вкладку.

### 1.2 Баги текущего кода, которые объясняют симптомы

1. **Терминалы в editor area плагину не видны.** `Terminal.editorViews` зовёт у
   `TerminalViewVirtualFile` метод `getTerminalView()` — его нет **ни в 262, ни в 263**; есть только
   `getTab(): TerminalToolWindowTab`. Следствие: оркестратор, перенесённый в редактор руками, не
   находится → агент открывается в тулвиндоу, «не в том окне».
2. **Окно висит после выхода агента.** Редактор терминала (`TerminalViewFileEditor`) закрывает себя
   сам только при `tab.closeOnProcessTermination == true`. Мы ставим `false`, а закрываем через
   `TerminalToolWindowTabsManager.closeTab`, который вкладку, ушедшую в редактор, не убирает.
   Агент, вышедший сам, не закрывается вообще никем.
3. `TerminalView.hasChildProcesses` — suspend-функция; рефлексия без аргументов её не находит, проверка
   всегда давала null.
4. Файл вкладки после переноса берётся из `selectedComposite` — ненадёжно; правильно — открытый
   `TerminalViewVirtualFile`, у которого `getTab()` — наша вкладка.
5. В 263 без `restoreOnProjectReopen(false)` вкладки агентов, вероятно, восстанавливаются после
   рестарта IDE пустыми шеллами. Без `userDefinedName(true)` заголовок вкладки перезаписывается
   заголовком процесса — а по заголовку мы ищем вкладку.

### 1.3 Как 2026.3 сама запускает агентов

`TerminalAgentsSupportKt.launchTerminalAgent` (модуль `intellij.terminal.frontend`):

```
createTabBuilder().shellCommand([путь к бинарю]).processType(NON_SHELL)
                  .tabName(displayName).closeOnProcessTermination(...).createTab()
content.setIcon(agent.icon)
```

`processType` и `shellCommand` есть и в 262. Это **официальный шаблон**, переходим на него: процесс
вкладки — сам агент (через `шелл -c`, см. §2.2), без печати строки запуска в pty. Следствия:
- argv идёт через API создания процесса, а **не через pty** → снимается ограничение «только ASCII»
  для строки запуска (кодировка JVM больше не участвует);
- процесс умер → вкладка закрылась сама (`closeOnProcessTermination = true`), в тулвиндоу и в
  редакторе одинаково, модального вопроса «в терминале что-то запущено» не бывает;
- не нужен хвостовой `; exit`, не нужно ждать shell integration перед печатью.

Список агентов IDE: `org.jetbrains.plugins.terminal.agent.TerminalAgent.getAllTerminalAgents()`
(точка расширения `terminalAgentProvider`): `agentKey` (`claude_code`, `codex`, `junie`, плюс
сторонние провайдеры), `displayName`, `binaryName`, `posixKnownLocationCandidates`, `icon`.
Доступность — `TerminalAgentsAvailabilityService.getAvailableAgents()` (кэш, не suspend). Только 263+.

Другие новинки 263, которые берём: `TerminalTabsManagerListener` (`tabAdded`, `tabDetached`,
`terminalViewCreated`) — событие «вкладку унесли в редактор» вместо опроса.

### 1.4 Codex 0.166 — проверено живьём

- **`codex queue --thread <uuid> --message <текст>` доставляет сообщение в живую интерактивную
  сессию**, она обрабатывает его новым ходом. Кириллица доезжает целой (проверено: «ПОНГ-ОК»).
  Это канал «оркестратор → Codex».
- Сессия Codex появляется в `~/.codex/session_index.jsonl` (`id`, авто-`thread_name`) и
  `~/.codex/sessions/YYYY/MM/DD/rollout-…-<id>.jsonl` (полная лента событий). Имя задаётся
  моделью, не нами → адрес Codex-агента — **UUID**, плагин держит соответствие «имя агента ↔ UUID».
- **Старт Codex блокируется интерактивными вопросами**: доверие к каталогу («Trust and continue»),
  затем доверие к хукам («Review hooks»). Во вкладке, которую никто не читает, это вечная
  блокировка. `-c projects."<dir>".trust_level="trusted"` вопрос о доверии **не снял**. Нужен
  эксперимент E1.
- Начальную задачу можно передать argv (`codex "<prompt>"`) — после перехода на NON_SHELL это
  безопасно по кодировке.

### 1.5 Обратный канал «агент → оркестратор-Claude»

У Claude Code нет CLI для отправки сообщения в сессию. Варианты:

| Вариант | Оценка |
|---|---|
| MCP **channels**: сервер с capability `experimental["claude/channel"]` шлёт `notifications/claude/channel` — сообщение вталкивается в сессию | Есть в 2.1.318, но сессия должна стартовать с `--channels` (allowlist, на Team/Enterprise — `channelsEnabled` в managed settings) или `--dangerously-load-development-channels` (диалог на старте). Плюс нашему HTTP-серверу нужен SSE. → **опциональный быстрый путь**, эксперимент E3 |
| Протокол сокета из реестра (`messagingSocketPath`, `.key`, `peer_send_signer`) | Недокументирован, подписан → **не берём**: ломается при апгрейде |
| **Почтовый ящик в плагине + `await_messages`** | Codex зовёт MCP-инструмент плагина `report`, плагин кладёт в ящик; оркестратор забирает `await_messages` (блокирующее ожидание волны). Точно ложится на модель tempo «запустил волну — дождался отчётов». → **основной путь** |

### 1.6 tempo 0.3.0 (разбор `skills/tempo`)

- Субагенты — обычный `Agent` без `subagent_type`; промпт «роль → правила → чтение → задача →
  отчёт»; модель явно в каждом запуске. Ограничения инструментов — **только словами в промпте**.
- Роли по шагам: `auditor` (LBS), `planner` (ADR→SDD, **диалог, а не один вызов** — та же живая сессия
  на правки), `implementer` (волна фаз, параллельно, без коммитов), `fixer` (тот же промпт),
  `gate` ×4 параллельно (tests/security/a11y/perf, «используй скилл <слот>»), `review` (скилл
  review-master), скиллы localization/translations.
- Результат: текстовый блок `STATUS: DONE | DONE_WITH_CONCERNS | BLOCKED` + `Создано/Изменено/
  Тесты/Замечания`, а гейты и ревью — файлом в каталоге фичи с `STATUS: PASS/FAIL` последней
  строкой. Коммитит только оркестратор. Штатной точки подмены механизма запуска нет.
- Отсюда главное про роли: **ограничения `tools:` в наших определениях ломают tempo** —
  белый список отрезает `Skill` (гейты зовут скиллы) и все MCP-инструменты (включая MCP IDE), а
  `disallowed-tools: Edit, Write` у скилла оркестратора мешает ему вести state/PROGRESS tempo.
  Это и есть «ограничения на старте, которые чаще мешали».

## 2. Этап 1 — стабилизация окон (Claude Code, 2026.3+)

### 2.1 Видимость терминалов в editor area
- `Terminal.editorViews`: `TerminalViewVirtualFile.getTab()` → `handleOf(tab)`, `editorFile = file`.
- Поиск файла вкладки: открытый `TerminalViewVirtualFile`, у которого `getTab() === handle.tab`
  (вместо `selectedComposite`). Один хелпер `Terminal.editorFileOf(project, handle)`.

### 2.2 Запуск агента процессом вкладки (NON_SHELL)
- Билдер: `processType(NON_SHELL)`, `shellCommand(argv)`, `closeOnProcessTermination(true)`,
  `restoreOnProjectReopen(false)`, `userDefinedName(true)`, `envVariables` как сейчас.
- argv: `[<шелл>, "-l", "-i", "-c", "<снятие маркеров>; exec <launchCommand> <флаги>"]` для POSIX,
  аналоги для PowerShell (`-NoLogo -Command`) и cmd (`/c`). Шелл — из настроек терминала IDE
  (`TerminalOptionsProvider.shellPath`, рефлексией), иначе `$SHELL`/`ComSpec`. Через шелл, а не
  бинарём напрямую: команда запуска — пользовательская (обёртка, `nvm use && claude`, функция из
  `.zshrc`), `-i` нужен ровно ради последнего. `exec` — только к хвосту команды (`a && exec b`
  невозможно склеить надёжно), поэтому `exec` ставим, только если команда простая; иначе шелл
  остаётся родителем — на закрытие это не влияет, он завершится вместе с агентом.
- `ShellDialect.exitWhenDone` и ожидание shell integration для агентов уходят. `ShellDialect`
  остаётся для формы `-c`/снятия переменных и для ручного режима.
- Иконка вкладки: `Content.setIcon(TerminalAgent(<key>).icon)` рефлексией; нет API — без иконки.
- Ограничение «только ASCII» остаётся у `brief_agent` (он по-прежнему печатает в pty).

### 2.3 Закрытие
- `close_agent`: команда выхода харнеса (`/exit`) → ждём исчезновения из реестра → ждём смерти
  процесса → вкладка закрывается сама. Страховка: если вкладка ещё открыта — закрыть явно (файл
  редактора через `FileEditorManager.closeFile`, вкладка тулвиндоу — `closeTab`); процесс уже мёртв,
  диалога нет.
- Если процесс не умер за таймаут — завершить его дерево (`ProcessHandle.descendants()` +
  `destroy`, затем `destroyForcibly`) и закрыть вкладку. Запись реестра к этому моменту уже ушла
  (после `/exit`), призрака не остаётся; если не ушла — сообщаем текстом.
- Агент вышел сам — вкладка закрывается сама (2.2). Плагин подчищает свои карты по
  `sessionState == Terminated` (опрос при обращении + слушатель, если есть).
- `hasChildProcesses` через рефлексию удаляется; потомков смотрим `ProcessHandle` по pid вкладки.
- Вкладки, которые плагин не запускал (оркестратор руками), — как раньше: не трогаем.

### 2.4 Размещение
- Родитель в editor area → агент соседней вкладкой в **его** `EditorWindow`, выбор возвращается на
  родителя (как сейчас, но окно ищется через 2.1 — то есть находится и у оркестратора,
  перенесённого руками).
- Родитель в тулвиндоу или не найден → агент **всё равно в editor area** (текущее окно или первое),
  а не в тулвиндоу: ради этого плагин и задуман. Нет ни одного окна редактора → тулвиндоу.
- `TerminalTabsManagerListener.tabDetached` — проверить, нужен ли он для надёжного момента
  «вкладка уже в редакторе» (263); если `openInEditor` синхронен — не используем.

### 2.5 Проверка этапа
- Автотесты: обновить `TerminalFlowTest`/`McpIntegrationTest` под NON_SHELL (FakeAgent как процесс
  вкладки), тест «агент вышел сам — вкладка закрыта», тест «перенесённая в редактор вкладка
  находится» (насколько позволяет `TestEditorManagerImpl`, §2.7.1 ARCHITECTURE).
- Сборка против 263 (локальная IDE); `sinceBuild = 263`.
- Живьём в песочнице 263: оркестратор в редакторе (перенесён руками) → `spawn_agent` → агент рядом,
  выбор не сбит → «ответь одним словом» → `close_agent` → окна нет; агент `/exit` сам → окна нет;
  рестарт IDE → вкладки агентов не восстановились.

## 3. Этап 2 — роли и скилл под tempo (только Claude)

### 3.1 Роли
Набор — по шагам tempo (§1.6):

| Роль | Имя | Шаги tempo | Время жизни |
|---|---|---|---|
| planner | `<pfx>-plan` | ADR, SDD, правки после гейта/ревью | долгоживущая, одна на фичу |
| implementer | `<pfx>-impl-<домен>` | фазы волны, fixer | пул; «Продолжай: P+1» — тот же агент |
| reviewer | `<pfx>-rev-<линза>` | gates, review ветки, MR-review | пул до 4; та же сессия на ревью дельты |
| researcher | `<pfx>-rsrch` | LBS (auditor), точечные вопросы | одна |

Оркестратор — роль только в смысле метки; включается `/orchestrate` поверх `/tempo`.

### 3.2 Определения ролей
- **Убрать `tools:` белые списки** у всех ролей и `disallowed-tools` у скилла оркестратора.
  Ограничения — словами, как в tempo («код не меняй», «не коммить», «пиши только отчёт»). Это
  возвращает агентам `Skill`, MCP IDE и прочие MCP.
- Промпт роли становится тонким: протокол команды (кому отвечать, формат ответа, не задавать
  вопросов в пустоту, не коммитить, MJC_REPORTS_DIR), а **содержание задачи** — промпт tempo
  дословно в брифинге.
- Формат ответа агента = формат tempo: блок `STATUS: …` последним; гейты/ревью — файл с
  `STATUS: PASS/FAIL` и путь в сообщении.
- `model` в определении остаётся дефолтом; модель из настроек роли (этап 3) и из `spawn_agent` её
  перебивает (`ANTHROPIC_MODEL` / `--model`).

### 3.3 Скилл `/orchestrate` как мост для tempo
Переписать: «в этой сессии tempo запускает субагентов так: вместо `Agent` — `list_agents` →
живой агент роли на этом участке получает задачу, иначе `spawn_agent(role, …)`; промпт tempo —
дословно; волна — все задачи одним ходом, затем дождаться всех ответов (SendMessage приходят сами,
от не-Claude — `await_messages`); коммитит оркестратор». Оговорить явно: это инструкция,
вызванная разработчиком, а не «требование чужого хука» (tempo такие игнорирует, §4 отчёта).
Правило экономии из ARCHITECTURE §1.1 сохраняется: правка — тому же агенту.

## 4. Этап 3 — харнесы и Codex

### 4.1 Модель харнеса (внутри плагина)
```kotlin
interface Harness {
    val key: String                    // agentKey IDE: claude_code, codex, junie…
    fun argv(spec: LaunchSpec): List<String>   // роль, модель, режим, задача, MCP
    fun env(spec: LaunchSpec): Map<String,String>
    fun awaitReady(spawn: SpawnContext): AgentAddress?   // реестр Claude / rollout Codex
    val exitCommand: String            // "/exit"
    val clearCommand: String?          // "/clear" | "/new"
    fun deliver(to: AgentAddress, text: String): DeliveryResult  // Claude: не нужен (SendMessage)
}
```
Адаптеры: `ClaudeHarness` (текущая логика), `CodexHarness`. Неизвестный ключ из IDE — в настройках
виден, но помечен «не поддерживается», в роль не назначается.

### 4.2 Настройки
- Список харнесов — из IDE (`TerminalAgent.getAllTerminalAgents()` + доступность). Нет API — плагин
  пишет об этом в диагностике, харнес по умолчанию `claude_code`. Ничего своего не храним, кроме привязок.
- Таблица ролей: роль → харнес, модель, режим прав (Claude: `--permission-mode`; Codex:
  `-s/-a`), доп. аргументы. Команда запуска на харнес (по умолчанию `claude` / `codex`,
  путь — из `knownLocationCandidates` IDE, если в PATH нет).
- `spawn_agent` получает необязательный `harness` (перебить привязку) — контракт расширяется, не
  ломается.

### 4.3 Codex-адаптер
- Запуск: NON_SHELL, `codex -C <проект> -m <модель> -s <sandbox> -a never
  -c mcp_servers.metajetcore.url=<наш MCP> [-c mcp_servers.<ide>.url=<MCP IDE>] "<роль + задача>"`.
- Роль: инструкции — первым промптом (или `-c developer_instructions=…`, эксперимент E2).
- Готовность и адрес: новый `rollout-*.jsonl` с `cwd` проекта после момента спавна; спавны Codex
  сериализуются, пока адрес не определён (иначе два параллельных старта не развести).
- Доставка: `codex queue --thread <uuid> --message <текст>` (процесс, не pty).
- Статус idle/busy: по ленте rollout (последнее событие — завершение хода или нет).
- Выход: `/quit` в pty (ASCII), затем ждём смерть процесса (вкладка закроется сама).

### 4.4 Почта (Codex → оркестратор)
- MCP-инструменты плагина:
  - `send_to_agent(name, text)` — оркестратор → агент любого харнеса (для Claude отвечает «используй
    SendMessage», чтобы не дублировать канал);
  - `report(text)` — для агентов не-Claude: кладёт сообщение в ящик их оркестратора (связь по
    `MJC_PARENT_SESSION`, переданной агенту в env и в MCP-URL-параметре);
  - `await_messages(names?, timeout_s)` — оркестратор ждёт ответов волны; возвращает по готовности
    или по таймауту «ещё в работе: …, вызови снова».
- Ящик — в памяти сервиса проекта + журнал в `MJC_REPORTS_DIR` (переживает перезапуск оркестратора).
- Быстрый путь E3 (channels): если оркестратор зарегистрировал наш сервер как channel —
  плагин вталкивает сообщение сам, `await_messages` не нужен.

### 4.5 Проверка этапа
Юниты: argv/окружение адаптеров, разбор rollout/индекса, ящик. Живьём: роль reviewer → Codex;
оркестратор `spawn_agent` → Codex «ответь одним словом» → `await_messages` получает ответ через
`report` → `send_to_agent` второй вопрос → ответ → `close_agent` → окна нет.


### 4.6 Итоги экспериментов и уточнённые решения (Codex 0.166)
Проверено живыми запусками в pty, до кода:

- **E1, доверие к каталогу.** `-c 'projects."<путь>".trust_level=…'` не работает, потому что ключ
  `-c` режется по точкам, а в пути они есть (`e.shatura`). Работает inline-таблица:
  `-c 'projects={"<путь>"={trust_level="trusted"}}'`, и вопроса нет. В `~/.codex/config.toml`
  ничего не пишем.
- **E1, хуки.** Вопрос «Review hooks» задаётся, когда у пользователя есть недоверенные хуки.
  `--dangerously-bypass-hook-trust` запустил бы непроверенный код, поэтому по умолчанию агентам
  передаётся `--disable hooks`. Это видно и меняется в настройках, в «доп. аргументах Codex».
- **E2, роль.** `developer_instructions` доезжает developer-сообщением. Передаётся профилем:
  плагин раскладывает `~/.codex/mjc-<role>.config.toml` (аналог `~/.claude/agents`) и запускает
  `codex -p mjc-<role>`. Длинный многострочный промпт в строке шелла не участвует.
- **Сессия Codex появляется только с первым сообщением.** Без промпта нет ни rollout, ни
  UUID, а значит и адреса для `codex queue`. Поэтому **задача Codex-агенту уезжает в argv при
  старте**, а для Claude по-прежнему идёт через SendMessage. В ответе `spawn_agent` так и сказано.
- **Переменные части команды идут через env вкладки:** задача, доверие, модель
  (`"$MJC_TASK"`, `"$MJC_CODEX_TRUST"`). Строка команды остаётся ASCII без пользовательского
  текста, кавычки и `$` в задаче доезжают целыми (проверено).
- **Обратный канал.** В rollout есть событие `task_complete` с `last_agent_message`, то есть ответ
  хода. Плагин читает его сам, и **инструмент `report` не нужен**: агенту не надо знать про
  наш MCP, конфиг MCP для Codex не требуется. `await_messages` читает ленты Codex-агентов
  с запомненного смещения. Журнал ящика пишется в `MJC_REPORTS_DIR`.
- **Статус** idle/busy — по последнему событию хода в rollout (`task_complete` или нет).
- **Сброс** (`reset_agent`) для Codex в 0.4 не поддерживается. `/new` меняет UUID треда, а новый
  rollout появится только со следующим сообщением. Ответ — текстом: «закрой и заведи нового».
- **E3 (channels)** откладывается: `await_messages` закрывает потребность tempo «волна → ждать всех».
- **E4** закрыт на этапе 1: `TerminalAgent` через рефлексию работает (иконка вкладки), список
  ключей берём оттуда же.
