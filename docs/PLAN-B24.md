# План: b24-cowork-code-cli как третий харнес

Цель — назначать роли (в первую очередь имплементеров) на b24-cowork-code-cli (Vibecode,
Kimi 3.1 Pro) так же, как сейчас на Codex: полноценная сессия во вкладке IDE, задачи от
оркестратора, ответы обратно. Оркестратор остаётся Claude. Контракт MCP-инструментов не
меняется — добавляется значение харнеса.

Основание — эксперименты `docs/EXPERIMENT-B24-CLI.md`. Здесь только то, что из них следует.

## 1. Что уже проверено (b24 0.26.7, macOS, под pty)

| Вопрос | Ответ |
|---|---|
| Задача после старта | `--input-file`: `{"type":"submit","text":…}`, кириллица цела |
| Ответ агента | `--json-file`: блоки `assistant` (`text`) до `stream_event/message_stop` |
| Конец хода | `message_stop` сообщения **без** `tool_use`; у сообщения с инструментом `stop_reason=tool_use`, ход продолжается. `result` в интерактиве нет |
| `submit` посреди хода | вливается в текущий ход, отдельного `user` и `message_stop` нет |
| Адрес сессии | `--session-id <uuid>` соблюдается, приходит в `session_start` |
| Промпт роли | `--append-system-prompt "$MJC_ROLE_PROMPT"` — многострочный русский текст с кавычками доезжает |
| Первая задача | `-i "$MJC_TASK"` |
| Сброс контекста | `submit "/clear"` работает (контекст пуст), события в ленте нет |
| Закрытие | SIGTERM — выход за 0,3 с, `session_end` не пишется |
| Доверие к каталогу | в каталоге проекта вопроса не было |

Этап 0 (во вкладке IDE, `EXPERIMENT-B24-CLI.md` §4) пройден: TUI в NON_SHELL-вкладке
работает, `readScreen` его читает; `-m bitrix/bitrixgpt-6.5-agent` применяется; при
`--approval-mode default` запись файла даёт `control_request`, и `confirmation_response` из
input-файла его закрывает; SIGTERM закрывает вкладку за 0,3 с.

## 2. Решения

1. **Ключ харнеса `b24`**, отображаемое имя «B24 CoWork Code». В списке агентов терминала IDE
   его нет, поэтому в настройках он предлагается, когда команда запуска находится в PATH
   шелла, а не по списку IDE. Иконки IDE для него нет — вкладка без иконки.
2. **Адрес — свой UUID**, плагин генерирует его до запуска и передаёт `--session-id`. Поиск
   «новой сессии в каталоге после момента старта», как у Codex, не нужен, а с ним и
   сериализация спавнов.
3. **Файлы канала** — `<системный каталог IDE>/metajetcore/b24/<uuid>/{input,events}.jsonl`.
   Не в проекте (не попадут в git) и не в `~/.b24-cowork-code` (не наш). Удаляются при
   закрытии агента.
4. **Задача на старте — `-i "$MJC_TASK"`**, как у Codex через переменную окружения вкладки.
   Без задачи стартует пустым: в отличие от Codex сессия есть и без первого сообщения.
5. **Промпт роли — `--append-system-prompt "$MJC_ROLE_PROMPT"`**, текст из `Roles.promptFor(role,
   Harness.B24)`. Файлы ролей не пишем: у b24 нет проверенного аналога профилей Codex, а
   переменная окружения уже доказала, что доносит текст без экранирования.
6. **Доставка — дописать `submit` в input-файл, но только в простое.** Посреди хода b24
   вливает сообщение в текущий ход, и один ответ закрыл бы два ожидания оркестратора. Поэтому
   плагин держит исходящую очередь агента и сбрасывает её по `message_stop`. Для
   `send_to_agent` это прозрачно: ответ «поставлено в очередь, агент занят».
7. **Ответы — в общий почтовый ящик**, который уже читает `await_messages`. Читатель ленты —
   по образцу `Codex.RolloutReader`: дочитывает до последнего `\n`. Ход начат — `user` с
   текстом (не `tool_result`) или `message_start`; закончен — `message_stop` сообщения без
   `tool_use`. Ответ — `text`-блоки последнего сообщения хода (как `last_agent_message` у
   Codex); ход без текста — пустой ответ, чтобы оркестратор не ждал вечно.
8. **Права** — из общей настройки режима, с переводом в `--approval-mode`:
   `auto`→`auto`, `acceptEdits`→`auto-edit`, `plan`→`plan`, `bypassPermissions`→`yolo`,
   пусто → флаг не передаём. Пришедший `control_request` плагин сам не одобряет: в
   `list_agents` статус «ждёт разрешения: <инструмент>», решает человек в TUI.
9. **Закрытие — SIGTERM дереву процессов**, как у Codex. **Сброс — `submit "/clear"`** (в
   отличие от Codex сброс поддерживается).
10. **Модель** — `-m <модель>`, если задана в настройке роли; модели Claude отбрасываются,
    как для Codex. Каталог для настроек — `modelProviders.openai[].id` из
    `~/.b24-cowork-code/settings.json` (файл читаем, не пишем).
11. **Обобщение вместо третьей копии.** В `AgentManager` Codex сейчас — отдельная карта
    `codexAgents` и ветки `if codex`. Вводим «внешний агент» с операциями
    `deliver / readReplies / busy / reset / close`, Codex переносим на него без изменения
    поведения, b24 — вторая реализация. Иначе каждая ветка (list, close, reset, await)
    обрастёт третьим случаем.
12. **Панель итогового ревью** получает b24 автоматически: она перебирает `Harness.entries`.

## 3. Этапы

Каждый этап — сборка и тесты фичи (`TerminalFlowTest`, юниты затронутых классов), один прогон
за раз. Следующий не начинается, пока предыдущий не зелёный.

**Этап 0. Живые проверки во вкладке IDE** — пройден платформенным тестом-пробой (лёгкая задача).
TUI b24 в NON_SHELL-вкладке рисуется и принимает ввод; `--approval-mode default` даёт
`control_request` на правку файла; `-m` с именем модели Vibecode. Результаты — в
`EXPERIMENT-B24-CLI.md`. Если TUI во вкладке неработоспособен — план останавливается.

**Этап 1. Обобщение внешнего агента.** Интерфейс внешнего агента в `agents/`, Codex
переезжает на него. Поведение не меняется: зелёные `testCodexAgentLifecycle`,
`testFinalReviewOpensTheWholePanel` и юниты Codex.

**Этап 2. Адаптер b24.** `harness/B24.kt`: каталог канала, argv, окружение, читатель ленты,
исходящая очередь. `Harness.B24`, настройки `b24LaunchCommand` / `b24Args`, ветка спавна,
`Roles.promptFor` для b24 (протокол ответа — как у Codex: «ответ — последнее сообщение хода»).
Тесты: юниты разбора ленты и argv; `TerminalFlowTest` с подставным `FakeB24` (пишет
`session_start`, отвечает на `submit`, умирает по SIGTERM) — полный цикл spawn → send →
await → reset → close без сети.

**Этап 3. Настройки и скилл.** Экран настроек: b24 в выборе харнеса роли и в панели
ревью, поле команды запуска. Скилл оркестратора: «не-Claude агенты (Codex, b24)» вместо
«Codex» — канал тот же (`send_to_agent` / `await_messages`); `reset_agent` для b24 работает.
Описания `send_to_agent` / `await_messages` в `McpTools` — текстом, сигнатуры те же.
Документы: `PLUGIN-SPEC.md` (значение харнеса), `ARCHITECTURE.md` (раздел b24),
`plugin/README.md`.

**Этап 4. Живой прогон** — пройден платформенным тестом через `McpTools` (не песочницей —
тот же код без ручного оркестратора), `EXPERIMENT-B24-CLI.md` §5. Песочница: имплементер на b24 с лёгкой задачей от оркестратора,
второй ход через `send_to_agent`, `reset_agent`, `close_agent`. Затем `verifyPlugin` против
263.6949 и 263.7307, сборка версии. `verifyPlugin`: 0.6.0 — Compatible на PS-263.6949 и
PY-263.7307.101.

## 4. Риски

- **Флаги внутренней сборки могут смениться.** Разбор ленты терпимый: неизвестное событие
  пропускается, худший исход — агент «молчит». `diagnostics` показывает версию b24.
- **Висящий `control_request`** при режиме `default` — агент ждёт человека. Смягчение —
  статус в `list_agents`; рекомендуемый режим для b24 — `auto`.
- **Нет `session_end` по SIGTERM** — смерть агента определяем по процессу вкладки, не по
  ленте (так же, как сейчас).
