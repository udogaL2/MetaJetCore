# Состав итогового ревью — план

Запрос: на итоговое ревью разработчик обычно ставит двух ревьюверов — Claude и Codex. Нужно
задавать, какие харнесы и сколько.

## Решения

| Вопрос | Решение |
|---|---|
| Где действует состав | Только итоговое ревью: шаг `review` у tempo и ревью MR (`domain=review`). Гейты `tests/sec/a11y/perf/scen` — по одному ревьюверу, как раньше: их в фиче много, умножать каждый незачем |
| Как заводится | Один вызов `spawn_agent(role=reviewer, domain=review)` без `harness` и `name` открывает весь состав и возвращает все имена. Оркестратору не нужно знать настройки и легко не «забыть второго». Явный `harness` или `name` — один агент, как раньше |
| Состав пуст | Поведение до изменения: один ревьювер на харнесе роли |
| Имена | `<pfx>-rev-review-claude`, `<pfx>-rev-review-codex`; при нескольких одного харнеса — `-2`, `-3` |
| Файлы отчётов | Плагин дописывает каждому участнику в задачу: «ты один из N; файл отчёта — с суффиксом твоего имени». Иначе два ревьювера писали бы в один путь из промпта tempo. Для Codex это единственный способ — задача уходит ему при старте |
| Сведение | Первый Claude-участник получает пути остальных отчётов и пишет итоговый файл по пути из промпта tempo: находки объединены, дубли схлопнуты, расхождения отмечены, `FAIL`, если `FAIL` хотя бы у одного. Оркестратор код и отчёты не пишет (ARCHITECTURE §5.1) |
| Повторное ревью дельты | Тем же участникам, всем — как и с одиночным ревьювером |

## Этапы

1. **Настройки.** `reviewPanel` (харнес → сколько, 0–3) и `reviewPanelModel` (харнес → модель).
   Экран: группа «Итоговое ревью» — строка на харнес: число, модель со списком.
2. **Спавн состава.** `McpTools.spawnAgent`: распознать итоговое ревью, развернуть состав,
   спавнить по одному (Codex — с задачей в argv), частичный отказ — текстом, остальные живут.
   Ответ — все имена, что сделать с каждым и кто сводит.
3. **Скилл.** Мост tempo: строка `review` — «один вызов заводит весь состав, сведение — первому
   Claude-участнику».
4. **Тесты** (разворот состава, имена, приписка к задаче; спавн состава на FakeAgent + FakeCodex),
   PLUGIN-SPEC, ARCHITECTURE §5.3, проверка в песочнице.

## Итог

Сделано всё по этапам 1–4.

- Настройки: группа «Итоговое ревью» — число и модель на харнес; Codex в группе, если он
  доступен в IDE или уже задан.
- `spawn_agent(reviewer, domain=review)` разворачивает состав, ответ называет всех и того,
  кто сводит.
- Скилл: строка `review` моста и абзац про состав.
- Тесты: `MjcSettingsTest` (разворот, порядок, слоты, ограничение 0–3, модель),
  `TerminalFlowTest.testFinalReviewOpensTheWholePanel` (FakeAgent + FakeCodex, приписка
  доехала до Codex) — зелёные.
- Живой прогон с настоящими ревьюверами не делали: поведение каждого участника то же, что у
  одиночного ревьювера, новое только в спавне — его покрывает тест.
