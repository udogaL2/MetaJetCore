# План: общение только внутри группы своего метаоркестратора

**Статус:** реализовано в 0.6.2, этапы 1–5. Контракт — PLUGIN-SPEC §1.0, обоснование — ARCHITECTURE §8.0.

Группа — метаоркестратор и агенты, которых **он** запустил через `spawn_agent`. Всё, что плагин
делает с агентами и что говорит моделям об адресатах, ограничено группой вызывающего. Чужие
агенты, чужие оркестраторы и личные сессии разработчика для группы не существуют.

## Что сломано сейчас

1. **Сессию Codex-агента угадывали** по свежей ленте в каталоге — агентом стала личная сессия
   Codex разработчика (16.11). Исправлено в `6d25793`: лента — по процессу вкладки.
2. **`list_agents` показывает все сессии Claude в каталоге проекта**, включая личные сессии
   разработчика и агентов других оркестраторов. Оркестратор принимает их за своих и пишет им.
3. **Вызывающего плагин знает только в `spawn_agent`.** `send_to_agent`, `await_messages`,
   `close_agent`, `reset_agent`, `focus_agent`, `brief_agent`, `read_tab` работают с любым
   агентом проекта: можно закрыть, сбросить или забрать ответы чужого агента.
4. **Список «агенты той же роли»** в ответе `spawn_agent` и в выборе «кому отдать задачу» —
   по всему проекту.
5. **Адресация по имени.** Имена не уникальны и меняются (`/rename`). Роль агента прямо
   велит: «нет MJC_PARENT — найди сессию с ролью orc через ListAgents», то есть любого
   оркестратора. `SendMessage` по имени уходит первому совпавшему.
6. **Членство в группе живёт только в памяти IDE.** Перезагрузка плагина (обновление без
   рестарта IDE) — и плагин не знает своих агентов, хотя они живы.

## Проверено

- Каждая сессия Claude Code слушает свой сокет: `messagingSocketPath` в записи реестра
  (`/tmp/cc-socks/<pid>.sock`). `SendMessage(to: "uds:<путь>")` доставляет ровно этой
  сессии — так плагин-разработчик сегодня писал «инт html» и claudiki-2e. Адрес уникален, в
  отличие от имени, и не меняется при `/rename`.
- Вызывающего по TCP-соединению плагин определяет надёжно (`CallerResolver`, 0.6.1).

## Решения

1. **Группа — сущность плагина, хранится на диске.** `TeamStore`:
   `~/.claude/metajetcore/<проект>/team.json`, запись на агента: имя, харнес, роль, модель,
   sessionId, pid процесса вкладки, владелец (sessionId оркестратора), для Codex — путь ленты,
   для b24 — каталог канала. Владелец группы — sessionId вызывающего; вместе с ним храним pid
   и `procStart` его процесса: `/clear` меняет sessionId у того же процесса, и группа
   переезжает на новый sessionId, а не теряется. Файл — плагина, не Claude Code.
2. **Вызывающий определяется на каждом вызове инструмента.** Не определился — инструменты,
   работающие с агентами, отказывают текстом («не удалось определить твою сессию…»), а не
   работают по всему проекту. Связь наугад хуже отсутствия связи.
3. **Каждый инструмент работает только с группой вызывающего.** `list_agents` — только
   группа; `send_to_agent`, `await_messages`, `close/reset/focus/brief_agent`, `read_tab` —
   чужое имя даёт «нет такого агента в твоей группе». Список агентов той же роли в
   `spawn_agent` и ревью-панель — тоже по группе. Проверка имени на занятость при спавне
   остаётся глобальной: два агента с одним именем путали бы людей.
4. **Точные адреса вместо имён.**
   - Агент получает `MJC_PARENT_ADDRESS=uds:<сокет оркестратора>` и отвечает **только** на
     него. Совет «найди orc через ListAgents» убирается.
   - `spawn_agent` и `list_agents` отдают оркестратору адрес каждого Claude-агента;
     скилл и роль оркестратора велят писать только на адреса из этих ответов и никогда — на
     сессии из `ListAgents`, которых нет в `list_agents`.
   - Роли агентов: писать только оркестратору по адресу из `MJC_PARENT_ADDRESS` и агентам,
     адреса которых он сам дал в задаче; другим сессиям — никогда.
5. **Восстановление после перезагрузки плагина.** При первом обращении `TeamStore` читается:
   Claude-агент жив — его sessionId есть в реестре; Codex — жив pid, лента читается с конца;
   b24 — жив pid, канал на месте. Мёртвых вычёркиваем. Вкладку находим по pid.
6. **Контракт инструментов** — сигнатуры прежние, меняются смысл (группа) и тексты ответов
   (адрес, отказ для чужого).

## Не делаем

- Заставить платформенные `ListAgents`/`SendMessage` видеть только группу — это не наш код.
  Защита там — правила в ролях и скилле плюс точные адреса, которые выдаёт плагин.
- Связь по имени (`parent`) больше не используется ни для чего — только пишется в журнал.
  Вызывающего не определили — отказ.

## Этапы

1. `TeamStore` + `SessionRecord.messagingSocketPath` + юниты.
2. Вызывающий на каждом инструменте, фильтр по группе во всех операциях `AgentManager`.
3. Адреса: окружение агента, ответы `spawn_agent`/`list_agents`, тексты ролей и скилла.
4. Восстановление группы после перезагрузки плагина.
5. Тесты: два оркестратора в одном проекте не видят и не трогают агентов друг друга; личная
   сессия в каталоге не попадает в `list_agents`; группа переживает `/clear` владельца и
   перезагрузку плагина. Документы: PLUGIN-SPEC, ARCHITECTURE, README, CLAUDE.md.

## Риски

- `uds:`-адрес — форма, которую печатает сама платформа в `from` входящих сообщений; если
  платформа её сменит, Claude-агенты откатятся на имя `MJC_PARENT`. Проверяем живьём.
- Вызывающий через прокси не определяется — теперь это отказ, а не работа по проекту.
