# MetaJetCore plugin — контракт

Дополнение к `docs/ARCHITECTURE.md`. Здесь только то, что нужно для реализации и что
проверяется тестами.

Плагин для JetBrains IDE **2026.3+**, Kotlin, JDK 21. Поднимает локальный MCP-сервер, к
которому подключается сессия-оркестратор.

Каждый агент — **полноценная отдельная сессия** в своей вкладке: Claude Code или, если так
задано для роли, Codex. Субагенты (инструмент `Agent`) в схеме не участвуют. Оркестратор —
всегда Claude Code.

```xml
<depends>com.intellij.modules.platform</depends>
<dependencies>
    <plugin id="org.jetbrains.plugins.terminal"/>
    <module name="intellij.terminal.frontend"/>
</dependencies>
```

Зависимость на модуль обязательна: API переработанного терминала живёт в нём, и без записи в
дескрипторе classloader плагина его не видит. Сами вызовы всё равно идут рефлексией — чтобы
смена сигнатур давала ручной режим, а не `NoSuchMethodError`.

---

## 1. MCP-инструменты

Всё возвращается **текстом**: оркестратор читает результат как обычный ответ инструмента, а
не разбирает JSON. Исключений из этого правила нет, ошибки тоже текст (с `isError`).

### `spawn_agent`

```
spawn_agent(
    role:     "orchestrator" | "planner" | "implementer" | "researcher" | "reviewer",
    parent:   string,   # имя ТВОЕЙ сессии (первая строка ListAgents)
    task:     string,   # брифинг; Claude-агенту НЕ доставляется, Codex-агенту — да, см. ниже
    name?:    string,   # по умолчанию <prefix>-<роль>[-<домен>]
    model?:   string,   # по умолчанию из настроек роли, затем из таблицы ролей
    domain?:  string,   # be / fe / p1 / tests / sec — различает агентов одной роли;
                        # reviewer + review — итоговое ревью составом, см. ниже
    harness?: "claude_code" | "codex",   # по умолчанию из настроек роли
) -> текст: имя, sessionId, pid + что делать с задачей дальше
```

Последовательность:

0. Привести `parent` к имени из реестра: `ListAgents` печатает его с ref-хвостом
   (`слитие мастера [815818]`), а в реестре хвоста нет — ARCHITECTURE §2.1.1. То же
   приведение применяется к `name` во всех остальных инструментах.
1. Снять список живых агентов этой роли — до открытия вкладки, иначе в него попадёт сам
   новичок. Спавн он не отменяет, но уедет в ответ предупреждением (см. ниже).
2. Сгенерировать имя и проверить, что оно не занято живой сессией.
3. Открыть вкладку терминала (`TerminalToolWindowTabsManager.createTabBuilder()`), передав
   окружение через `envVariables`:
   ```
   CLAUDE_CODE_SESSION_NAME = <name>      # адрес для SendMessage
   ANTHROPIC_MODEL          = <model>
   CLAUDE_CODE_AGENT        = <role>      # только метка в реестре, роль НЕ задаёт
   MJC_REPORTS_DIR          = <каталог отчётов вне репозитория>
   MJC_PARENT_SESSION       = <sessionId оркестратора>   # КЛЮЧ связи, если определился
   MJC_PARENT               = <имя оркестратора>         # справочно; ключа нет, если родителя нет
   ```
   Связь задаёт `sessionId`, а не имя: имя не уникально, меняется и переиспользуется
   (ARCHITECTURE §2.1.1). `MJC_PARENT_SESSION` может отсутствовать при непустом
   `MJC_PARENT` — это значит «родителя однозначно определить не удалось», и получатель
   обязан считать связь неизвестной, а не достраивать её по имени. Разбор для стороннего
   наблюдателя — `docs/CLAUDIKI-PARENT-LINK.md`.
4. Если вкладка родителя живёт в editor area — открыть новую рядом с ней
   (`TerminalInEditorSupport.openInEditor`), иначе оставить в тулвиндоу.
5. Дождаться, пока `sessionState` вкладки станет `Running`.
6. Напечатать команду запуска — **только ASCII и только то, что нельзя задать окружением**:
   ```
   [снятие унаследованных маркеров; ]<launchCommand> --agent mjc-<role> --permission-mode auto
   ```
7. Дождаться появления `~/.claude/sessions/<pid>.json` с `name == <name>`; взять оттуда
   `pid`, `sessionId` и **фактическое имя** (при коллизии платформа переименует сессию).
8. Вернуть оркестратору имя и текст задачи с указанием отправить её через `SendMessage`.

Шаги 6–8 — для харнеса Claude Code. Codex-агент запускается иначе (§1.1).

**Claude-агенту задачу инструмент не доставляет намеренно.** Содержательный канал один — межсессионные
сообщения: они адресные, попадают в очередь агента и не зависят от того, что сейчас на экране
вкладки. Печать в TUI осталась управляющим командам и аварийному `brief_agent`.

Ошибки — текстом: имя занято, терминал недоступен, шелл не поднялся, сессия не появилась в
реестре. В последних трёх случаях возвращается готовая команда для ручного запуска.

**Про дубль роли.** Если на момент вызова той же ролью уже кто-то занят, успешный ответ
содержит их имена и напоминание: задачу по уже ведомому участку отдать живому агенту, а
лишнего закрыть. Это предупреждение, не отказ — несколько имплементеров по непересекающимся
доменам штатны, а различить «другая задача» и «та же задача, новый агент» плагин не может
(ARCHITECTURE §8.1).

**Итоговое ревью составом.** `role=reviewer`, `domain=review`, без `harness` и `name`, и в
настройках задан `reviewPanel` — один вызов открывает весь состав: по агенту на участника,
имена `<pfx>-rev-review-claude`, `<pfx>-rev-review-codex`, у второго одного харнеса `-2`,
`-3`. При составе больше одного к задаче каждого дописывается: «ты один из N, файл отчёта —
с суффиксом `-<слот>`», иначе все писали бы в один путь из промпта tempo. Отказ участника
состав не отменяет, ошибка — только если не поднялся никто. Ответ: секция на участника
(что делать с задачей — как для одиночного) и абзац СВЕДЕНИЕ — кому из участников (первому
Claude) отдать пути остальных отчётов, чтобы он свёл их в файл по исходному пути. Состав
пуст, или указан `harness`/`name` — один агент, как раньше.

### 1.1. Codex-агент

Харнес выбирается так: `harness` из вызова, иначе настройка роли, иначе Claude Code.
Оркестратор — всегда Claude Code. Модель Claude (`opus`, `sonnet`, `claude-*`), которую tempo
передаёт по привычке, для Codex отбрасывается: Codex её не знает и упал бы на старте.

У Codex нет межсессионных сообщений и нет сессии без первого сообщения, поэтому:

1. Задача едет **в командной строке**, но через окружение: `MJC_TASK` в `envVariables`,
   в строке — только ссылка на переменную (`"$MJC_TASK"`). Кавычки, `$`, кириллица доезжают
   как есть, строка остаётся ASCII.
2. Команда:
   ```
   <codexLaunchCommand> -p mjc-<role> <codexArgs> [-m "$MJC_MODEL"] -c "$MJC_CODEX_TRUST" "$MJC_TASK"
   ```
   Роль — профиль `~/.codex/mjc-<role>.config.toml` (`developer_instructions`), плагин
   переписывает его при старте IDE. `MJC_CODEX_TRUST` — inline-таблица
   `projects={"<каталог>"={trust_level="trusted"}}`: иначе Codex спросит о доверии.
3. Готовность — появление новой ленты `~/.codex/sessions/**/rollout-*.jsonl` с `cwd` проекта,
   начатой после спавна и не занятой другим агентом. Спавны Codex сериализуются: два
   одновременных старта в одном каталоге так не различить.
4. Адрес агента для плагина — имя, данное при спавне; внутри — UUID треда из ленты.
5. Ответы — `task_complete.last_agent_message` из ленты. Их отдаёт `await_messages` и
   дублирует журнал `mailbox.jsonl` в каталоге отчётов.

### `send_to_agent(name, text) -> текст`

Только для Codex-агентов: `codex queue --thread <id> --message <text>`, запущенный через шелл
с текстом в окружении (`MJC_MESSAGE`). Сообщение встаёт в очередь треда новым ходом. Для
Claude-агента возвращает ошибку с подсказкой писать `SendMessage` — молча доставить ему
другим путём значило бы завести второй содержательный канал.

### `await_messages(names?, timeout_s?) -> текст`

Ждёт завершённых ходов Codex-агентов. С `names` — пока ответит каждый (волна tempo), без —
первый ответ любого. `timeout_s` по умолчанию 45, максимум 120: держим ниже MCP-таймаута
клиента. По таймауту возвращает то, что пришло, и список тех, кто ещё работает, — вызов
повторяется. Ответы Claude-агентов сюда не попадают: они приходят оркестратору сами.

### `list_agents() -> текст`

Живые сессии в директории проекта: имя, роль (из `agent` реестра или из своей карты), модель,
харнес, статус (у Codex — по ленте: идёт ход или нет), pid, пометка «вкладка не под управлением плагина». Записи мёртвых процессов
отфильтрованы: файл в реестре остаётся после падения сессии. К списку добавлено напоминание
отдавать задачу по уже ведомому участку живому агенту, а не заводить на то же место нового.

### `brief_agent(name, text) -> текст`

Впечатывает текст во вкладку как ввод пользователя (bracketed paste + Enter). **Аварийный
канал**: обычная переписка — `SendMessage`.

### `reset_agent(name) -> текст`

Печатает `/clear`. Новую задачу оркестратор отправляет сам. Применяется при переходе между
этапами; внутри этапа сохранённый контекст — главная экономия схемы.

Для Codex-агента — отказ текстом: сбросить тред без нового первого сообщения нельзя. Нужен
чистый контекст — `close_agent` и новый `spawn_agent`.

### `close_agent(name) -> текст`

`/exit` → ждать исчезновения записи из реестра → ждать смерти процесса вкладки → закрыть
вкладку. Процесс никогда не убиваем: останется запись в реестре и мёртвый пайп, и
`ListAgents` будет показывать призрака.

Три исхода:

| Ответ | Что произошло |
|---|---|
| `'<имя>' завершён, вкладка закрыта` | нормальный путь |
| `сессия '<имя>' завершена, но во вкладке остался живой процесс…` | агент закрыт, вкладку закрыть нельзя: IDE спросила бы подтверждение модальным диалогом и подвесила бы этот вызов. Вкладка остаётся под управлением — её экран доступен через `read_tab` |
| `вкладка '<имя>' плагину неизвестна` (ошибка) | имени нет в карте вкладок |

Второй случай — не ошибка: агент завершён, повторять вызов бессмысленно. Возникает там, где
вкладку запускал не плагин (подхвачена по дереву процессов, перезапущена руками) или где агент
оставил после себя живого потомка.

**Codex закрывается сигналом.** `/quit` в терминале IDE до него не доходит (в голом pty
работает — проверено), а реестра, где осталась бы запись-призрак, у Codex нет. Поэтому:
дочитать ленту (последние ответы уходят в `mailbox.jsonl`) → SIGTERM дереву процессов
вкладки → закрыть вкладку. Занимает доли секунды.

### `focus_agent(name) -> текст`

Показать вкладку разработчику.

### `read_tab(name) -> текст`

Хвост экрана вкладки (последние ~4000 символов). Для случая «агент поднялся, но молчит»:
увидеть, на каком интерактивном вопросе он встал, можно только так.

### `diagnostics() -> текст`

Что разрешилось из терминального API, какие переменные вычищаются, сколько вкладок под
управлением, пример команды для ручного режима.

## 2. Настройки плагина

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `launchCommand` | `claude` | обёртка пользователя; обязана пробрасывать `"$@"` |
| `permissionMode` | `auto` | флаг `--permission-mode`; пусто — не добавлять |
| `namePrefix` | аббревиатура проекта | `MetaJetCore` → `mjc` |
| `readyTimeoutSeconds` | `45` | ожидание записи в реестре; держим ниже MCP-таймаута |
| `stripApiKeys` | `true` | снимать `ANTHROPIC_*` |
| `stripInheritedClaudeMarkers` | `true` | снимать `CLAUDE*` |
| `extraEnvRaw` | пусто | дополнительные переменные, `KEY=VALUE` построчно |
| `mcpPort` | `0` | 0 — вывести из пути проекта, чтобы порт был стабильным |
| `roleHarness` | пусто | роль → `claude_code` / `codex`; нет записи — Claude Code. Список выбора берётся у IDE (агенты терминала), назначить можно только харнес с адаптером |
| `roleModel` | пусто | роль → модель; пусто — по таблице ролей (Claude) или из конфига Codex |
| `reviewPanel` | пусто | харнес → сколько ревьюверов итогового ревью (0–3); пусто — один ревьювер на харнесе роли |
| `reviewPanelModel` | пусто | харнес → модель участников состава; пусто — модель из вызова, затем роли |
| `codexLaunchCommand` | `codex` | команда или обёртка Codex |
| `codexArgs` | `-s workspace-write -a never --disable hooks` | `-a never` — вопрос о подтверждении во вкладке, которую никто не читает, это вечная блокировка; `--disable hooks` — иначе Codex спросит «Review hooks» на старте |

Диалект шелла настройкой не задаётся: он определяется по фактическому процессу вкладки
(`startupOptionsDeferred.shellCommand`).

## 3. Карта вкладок

1. **Основной путь.** Вкладки, созданные плагином (`spawn_agent`, «New Orchestrator Here»),
   лежат в карте `имя → вкладка`.
2. **Запасной.** Для сессий, запущенных руками: `startupOptionsDeferred.pid` даёт pid шелла
   вкладки, реестр — pid процесса `claude`; если шелл среди предков claude, сессия живёт в
   этой вкладке. Если и это не сработало — сравнение с заголовком вкладки.

Разместить агента рядом можно только с тем родителем, который живёт в editor area. Поэтому
действие **New Orchestrator Here** сразу переносит вкладку туда: у запущенной руками вкладки
в тулвиндоу «рядом» не существует.

## 4. Что осталось нереализованным

- `restart_agent` (close + spawn с теми же параметрами).
- Сброс контекста Codex-агента.
- Харнесы кроме Claude Code и Codex: IDE их покажет, но адаптера (запуск, готовность,
  доставка) у плагина нет.
- Наблюдение за реестром: сейчас плагин опрашивает его только внутри операций, а событий
  «агент умер» / «агент ждёт ввода» не отслеживает.
- Восстановление раскладки после рестарта IDE.
