# MetaJetCore plugin

Плагин для JetBrains IDE **2026.3+**. Открывает рядом с сессией-оркестратором вкладки с
другими полноценными сессиями — Claude Code, Codex или b24-cowork-code-cli — и управляет их жизненным циклом.

Дизайн — `../docs/ARCHITECTURE.md`, контракт инструментов — `../docs/PLUGIN-SPEC.md`.

## Сборка

Нужен JDK 21 (подойдёт JBR из любой IDE 2025+). Gradle wrapper лежит в репозитории.

```bash
cd plugin
./gradlew buildPlugin        # zip в build/distributions/
./gradlew runIde             # песочница с плагином
./gradlew verifyPlugin       # совместимость: с MJC_LOCAL_IDE — с ней, иначе с рекомендованными IDE
```

Версии инструментов связаны и меняются вместе: IntelliJ Platform Gradle Plugin 2.18 требует
Gradle 9+, Gradle 9 — Kotlin 2.2+, а он — foojay-resolver 1.0+ (на 0.8.0 сборка падает с
`NoSuchFieldError: IBM_SEMERU`). Артефакт платформы — `intellijIdea(<сборка 263>)`, переопределяется
свойством `mjcIdeVersion`: Community (`IC`) с 2025.3 больше не публикуется, а песочница
платной IDE встаёт на диалоге лицензии.

**Если ничего не скачивается** — `download.jetbrains.com` отвечает 451, `cache-redirector`
даёт `Read timed out`, — первым делом проверьте прокси. **JVM не читает `HTTP_PROXY` и
`HTTPS_PROXY` из окружения**: curl через прокси ходит, а Gradle идёт напрямую и упирается в
блокировку. Лечится строками в `~/.gradle/gradle.properties`:

```properties
systemProp.https.proxyHost=<хост>
systemProp.https.proxyPort=<порт>
systemProp.https.proxyUser=<логин>
systemProp.https.proxyPassword=<пароль>
systemProp.http.nonProxyHosts=127.0.0.1|localhost
```

Свойства `-Dhttps.proxyHost=…` можно передать и в командной строке `./gradlew`.

Второй путь, если платформу всё равно не достать, — собирать против уже установленной
IDE 263+ (бесплатной или EAP, чтобы песочница не спрашивала лицензию):

```bash
MJC_LOCAL_IDE=~/.local/share/JetBrains/Toolbox/apps/phpstorm ./gradlew buildPlugin
```

То же значение можно положить свойством `mjcLocalIde` в `~/.gradle/gradle.properties`.
В репозитории пути к чужим машинам не хранятся, поэтому источник платформы задаётся снаружи.

## Релизы

Версия задаётся в одном месте — `version` в `build.gradle.kts`. Из неё берутся и имя zip, и
версия в `plugin.xml`, поэтому руками их править не нужно и нельзя: разъедутся.

```bash
# 1. Поднять версию в build.gradle.kts, например 0.1.0 -> 0.2.0
# 2. Прогнать тесты, собрать и проверить — в том числе против самой старой сборки 263
#    (путей может быть несколько, через `:`). Без неё верификатор пропускает поломки, которые
#    вылезают только на старых сборках: так 0.5.0 падала в PhpStorm 263.6949.
./gradlew test buildPlugin        # zip в build/distributions/metajetcore-<версия>.zip
MJC_VERIFY_IDES="<путь к старой IDE 263>" ./gradlew verifyPlugin
# 3. Закоммитить, поставить тег и отправить
git tag v0.2.0 && git push origin master --tags
# 4. GitHub -> Releases -> Draft a new release -> тег v0.2.0 -> приложить zip
```

Тег и версия обязаны совпадать: иначе через полгода не понять, какой архив какому коду
отвечает. `sinceBuild` при этом не трогаем без причины — 263 это нижняя граница API
агентов терминала и NON_SHELL-вкладок, а верхней границы нет намеренно.

Обновление у пользователя ничего не требует: скилл `/orchestrate`, определения ролей и
профили Codex плагин переписывает при каждом старте IDE, а MCP-подключение перепроверяет и чинит сам.

Если захочется, чтобы IDE показывала список изменений в окне обновления плагина, — это поле
`changeNotes` в `pluginConfiguration`. Сейчас его нет намеренно: оно требует ручного текста на
каждый релиз, а описание релиза на GitHub эту роль уже выполняет.

## Установка

`Settings | Plugins | ⚙ | Install Plugin from Disk…` и указать zip из `build/distributions/`.
Дальше ничего: плагин сам прописывает своё MCP-подключение в `~/.claude.json` для этого
проекта. Если не смог — покажет уведомление с готовой командой.

## Подключение оркестратора

1. `Tools | MetaJetCore | New Orchestrator Here` — вкладка сразу попадает под управление
   плагина и переезжает в editor area, чтобы агентам было где появиться рядом.
2. В этой вкладке вызвать `/orchestrate`.

Скилл `orchestrate` плагин ставит в `~/.claude/skills/orchestrate/` при старте IDE и обновляет
при каждом запуске: он описывает инструменты плагина, поэтому их версии обязаны совпадать.
Роли агентов — туда же, в `~/.claude/agents/mjc-<role>.md`; для Codex — профили
`~/.codex/mjc-<role>.config.toml`.

## Как это устроено, коротко

**Роль оркестратора — скилл, роли агентов — флаг.** Обычные сессии Claude Code остаются
обычными; оркестратором сессия становится по вызову `/orchestrate`, в том числе посреди
разговора, когда контекст задачи уже набран. Дочерние агенты получают роль флагом
`--agent mjc-<role>`; определения плагин раскладывает файлами, и claude читает их сам как
UTF-8. Белого списка инструментов у ролей нет: он отрезал `Skill` и MCP IDE. Ограничения —
словами, как в tempo («код не меняй», «не коммить»).

**Агент — процесс вкладки.** Вкладка создаётся NON_SHELL с argv
`<шелл> -l -i -c '[unset …; ]exec claude --agent mjc-implementer --permission-mode auto'` — так
же IDE запускает своих агентов. Окружение едет через API вкладки (`envVariables`), в строке —
только роль и режим прав. Процесс умер — вкладка закрылась сама.

**Содержательный канал один — `SendMessage`.** В терминал уходят только управляющие команды
(`/exit`, `/clear`). У Codex и b24 `SendMessage` нет: задача едет при старте, ответы плагин читает
из ленты сессии (`await_messages`), следующие задачи — `codex queue` у Codex и input-файл у b24
(`send_to_agent`). `brief_agent` вставляет текст прямо во вкладку, но
это аварийный канал: он нужен, когда агент перестал отвечать на сообщения.

**Готовность определяется по реестру сессий**, а не по таймеру: `~/.claude/sessions/<pid>.json`
появляется тогда, когда `claude` поднялся и забиндил inbox-сокет, то есть готов и к вводу,
и к межсессионным сообщениям. Записи мёртвых процессов оттуда отфильтровываются по pid: файл
удаляет сама сессия при выходе, и после падения он остаётся.

## Terminal API: что используется

Проверено `javap` по jar-ам PyCharm 2026.2 (PY-262.9437.71) и 2026.3 (PY-263.7307).

| Что нужно | Чем делается |
|---|---|
| менеджер вкладок | `com.intellij.terminal.frontend.toolwindow.TerminalToolWindowTabsManager.getInstance(project)` |
| создать вкладку | `createTabBuilder()` → `processType(NON_SHELL)` / `shellCommand` / `envVariables` / `closeOnProcessTermination` / `restoreOnProjectReopen` / `userDefinedName` / `createTab()` |
| напечатать | `view.createSendTextBuilder().shouldExecute().useBracketedPasteMode().send(text)` |
| прочитать экран | `TerminalViewKt.activeOutputModel(view)` → `getText(start, end)` |
| готовность | `view.getSessionState()` → `NotStarted` / `Running` / `Terminated` |
| pid шелла и его argv | `view.getStartupOptionsDeferred()` → `getPid()`, `getShellCommand()` |
| перенос в editor area | `TerminalInEditorSupport.openInEditor(content, editorWindow)` |
| терминал в редакторе | открытый `TerminalViewVirtualFile` → `getTab()` |
| закрыть вкладку | сама, по смерти процесса; страховка — `manager.closeTab(tab)` / `closeFile` |
| харнесы IDE и иконки | `TerminalAgent.getAllTerminalAgents()` → `agentKey`, `displayName`, `icon` |

Классы живут в модуле `intellij.terminal.frontend` (`visibility="public"`), поэтому в
`plugin.xml` объявлена зависимость и на плагин терминала, и на его модуль: без этого
classloader плагина их не видит.

## Что сделано ради устойчивости к апгрейдам IDE

| Решение | Зачем |
|---|---|
| Terminal API только через рефлексию | классы модуля помечены `@Experimental`; смена сигнатуры даёт null и ручной режим, а не `NoSuchMethodError` |
| Нет `untilBuild` | плагин не отключается при апгрейде IDE; безопасно только благодаря рефлексии |
| Свой JSON вместо библиотеки | нечему конфликтовать с версией из платформы |
| `com.sun.net.httpserver` вместо HTTP платформы | JDK не меняется, внутренние API платформы меняются |
| Стабильный порт MCP из пути проекта | сохранённый `~/.claude.json` не начинает указывать в пустоту после рестарта |

Цена зависимости на модуль терминала: она обязательная, и при выключенном плагине терминала
MetaJetCore не загрузится. Размен осознанный — без терминала оркестрировать нечего.

Если что-то сломается — `Tools | MetaJetCore | Diagnostics` покажет, нашлось ли API нового
терминала, сколько вкладок под управлением и какие переменные вычищаются при запуске.

## Что проверяют тесты

Терминальный слой проверяется **на настоящей вкладке**, а не на моках: тесты регистрируют
тулвиндоу терминала и открывают вкладку через то же API, что и плагин. Вместо `claude`
запускается подставной агент (`FakeAgent`) — скрипт, который пишет запись в реестр сессий и
убирает её по `/exit`; вместо `codex` — `FakeCodex`, который пишет ленту сессии и понимает
`queue`; вместо b24 — `FakeB24`, который пишет ленту событий и читает input-файл. Поэтому тесты не ходят в сеть, не тратят лимиты
подписки и не зависят от версии CLI, но проверяют весь цикл:

- спавн: вкладка, окружение через API (имя сессии в записи реестра берётся из
  `CLAUDE_CODE_SESSION_NAME`), печать команды, ожидание записи;
- `/clear` и `/exit` доходят до уже запущенного процесса, после закрытия запись исчезает;
- не-ASCII в `brief_agent` отклоняется;
- экран вкладки читается;
- сессия, запущенная руками, находится по дереву процессов;
- спавн переживает отсутствие editor area;
- агент, вышедший сам, закрывает вкладку;
- итоговое ревью составом: один `spawn_agent` открывает Claude- и Codex-ревьювера, Codex
  получает задачу с припиской про свой файл отчёта (`TerminalFlowTest`), разворот состава
  из настроек (`MjcSettingsTest`);
- Codex-агент: спавн по ленте, ответ через `await_messages`, `send_to_agent`, закрытие сигналом;
- b24-агент на подставном `FakeB24`: задача и роль при старте, ответ — итог хода с инструментом,
  сообщение занятому агенту ждёт очереди и уходит отдельным ходом, `/clear`, закрытие с уборкой канала;
- формат ролей и скилла (`RolesTest`), разбор лент Codex (`CodexTest`) и b24 (`B24Test`).

**Чего тесты не покрывают: размещение агента рядом с оркестратором в editor area.** Платформа
в тестах подставляет `TestEditorManagerImpl`, у которого окон редактора нет вовсе (замер:
`окон=0` при открытом файле), поэтому проверить там нечего. Эта ветка проверяется прогоном в
песочнице руками — см. раздел «Статус».

Про потоки в тестах: тело платформенного теста выполняется в EDT, а блокирующие операции
плагина сами уходят в EDT. Звать их напрямую — взаимоблок; для этого есть
`onPooledThreadPumpingEdt`, который запускает работу на постороннем потоке и всё это время
крутит очередь событий, изображая живую IDE.

## Статус

**0.6.1.** Родитель агента — вызывающая сессия, определённая по TCP-соединению MCP-запроса, а не
имя из `parent`: после `/rename` оркестратора связь (`MJC_PARENT_SESSION`) больше не теряется.
Агент открывается рядом с оркестратором и тогда, когда тот живёт во вкладке AIR (Agent
Threads), а не в терминале, — раньше он уходил к активному окну. `docs/PLAN-CALLER.md`.

**0.6.0.** Третий харнес — b24-cowork-code-cli (Vibecode): роль назначается в настройках, как Codex;
канал — файлы «dual output» (`--input-file` / `--json-file`), ответы через `await_messages`,
задачи через `send_to_agent`, `reset_agent` работает. Codex переведён на общий «внешний агент»
без изменения поведения. План и проверки — `docs/PLAN-B24.md`, `docs/EXPERIMENT-B24-CLI.md`.

**0.5.2.** Совместимость со старыми сборками 263: в PhpStorm 263.6949 плагин не видел терминалов
в редакторе (`NoSuchFieldError` на `FileEditorManager.Companion`) — агент открывался у активного
окна, а не рядом с оркестратором. Проверено верификатором против 263.6949 и 263.7307.

**0.5.1.** Исправления:

- агент, перенесённый в редактор, больше не оставляет пустую вкладку в тулвиндоу Terminal;
- скилл: участнику состава ревью отправляется брифинг из ответа `spawn_agent` (с припиской
  про его файл отчёта), а не исходный промпт.

**0.5.0.** Поверх 0.4.0:

- экран настроек переделан: роли таблицей (харнес, модель), пояснения в подсказках, редкое
  свёрнуто;
- список моделей берётся у самого харнеса (`list_models` у Claude Code, `model/list` у
  Codex), без зашитого справочника;
- итоговое ревью составом: в настройках — сколько ревьюверов какого харнеса, один
  `spawn_agent(reviewer, domain=review)` открывает всех. Покрыто тестом на подставных агентах,
  живьём на настоящих `claude` и `codex` состав ещё не гоняли.

**0.4.0.** Собирается против 2026.3, тесты проходят, проверено живьём в песочнице PyCharm
2026.3 RC (263.7307) на реальных `claude` и `codex` — теми же MCP-вызовами, что делает
оркестратор.

Подтверждено живьём:

- агент поднимается процессом NON_SHELL-вкладки, окружение доезжает, ложится в editor area
  рядом с родителем, выбор остаётся на родителе;
- родитель, перенесённый в редактор руками, находится, `MJC_PARENT_SESSION` передаётся;
- `close_agent` закрывает окно (Claude — 1,4 с, Codex — 0,2 с); агент, вышедший сам, окна не
  оставляет; после рестарта IDE вкладки агентов не восстанавливаются;
- роли без белого списка: ресерчер вызвал `Skill` и MCP-инструмент IDE, ответил `SendMessage`
  со `STATUS: DONE`;
- Codex-ревьювер стартовал без вопросов (доверие, хуки), ответ пришёл через `await_messages`,
  `send_to_agent` с кириллицей и кавычками доехал дословно.

Не проверено: сопоставление вкладки по дереву процессов для оркестратора, запущенного руками;
Codex на Windows (`envRef` для PowerShell и cmd); Linux.
